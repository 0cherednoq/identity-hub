# Командная строка Identity Hub

Это справочник для разработчика или оператора, который запускает миграции и
фоновые процессы Identity Hub. Все команды выполняются через установленный
скрипт `identity-hub`; в uv-проекте добавляйте префикс `uv run`.

## Общие настройки

| Переменная | Назначение | Где используется |
|---|---|---|
| `IDENTITY_HUB_DATABASE_URL` | Async SQLAlchemy URL PostgreSQL | `migrate`, фабрика приложения |
| `IDENTITY_HUB_KEK` | `key_id:base64`; первый ключ активен | `EnvSecretsProvider` в фабрике |
| `IDENTITY_HUB_FACTORY` | `package.module:callable` | Все команды, кроме `migrate` |

Значения `IDENTITY_HUB_KEK` и пароли в URL не передавайте аргументами процесса и
не пишите в логи. Для Docker/Kubernetes secrets можно использовать
`FileSecretsProvider` внутри фабрики.

> **Пароль в `--url`.** Аргументы процесса видны всем пользователям машины (`ps`, `/proc`,
> диспетчер задач) и попадают в историю shell и логи CI. Адрес базы с паролем передавайте
> через `IDENTITY_HUB_DATABASE_URL`. Если пароль всё же указан в `--url`, `migrate`
> печатает предупреждение.

Фабрика без аргументов должна вернуть `IdentityHub` или awaitable с ним. CLI сам
вызывает `hub.start()`:

```python
# app/identity.py
from identity_hub.hub import IdentityHub


async def create_hub() -> IdentityHub:
    return IdentityHub(...)
```

```bash
export IDENTITY_HUB_FACTORY=app.identity:create_hub
```

## `migrate`

Применяет внутреннюю ветку миграций до `head`:

```bash
export IDENTITY_HUB_DATABASE_URL=postgresql+asyncpg://app:password@db/app
identity-hub migrate --db-schema identity_hub
```

Адрес можно передать и аргументом `--url` — без пароля (например, при входе по
сертификату или через `PGPASSWORD`). `--db-schema`
создаёт отдельную схему, если её ещё нет. `--revision` полезен только для
контролируемого развёртывания конкретной ревизии.

Миграция берёт PostgreSQL advisory lock на схему на всё время upgrade: параллельные
`migrate` (несколько подов с init-job) выполняются по очереди, второй видит уже готовую
схему. Блокировка транзакционная и снимается при commit или ошибке. Обычная работа
приложения этот lock не берёт.

## `dispatcher`

Доставляет Python-события, вебхуки и уведомления, а также запускает due-задачи:

```bash
identity-hub dispatcher --factory app.identity:create_hub
identity-hub dispatcher --once
```

Без `--once` процесс работает до отмены. Доставка at-least-once: пользовательские
callback и принимающие системы должны дедуплицировать побочные эффекты.

Постоянный процесс переживает сбои: потеря соединения с базой или другая ошибка цикла
пишется в лог (`dispatcher: сбой цикла (<тип ошибки>), повтор через N с`) и в счётчик
`identity_hub_failures_total{scope="dispatcher", reason="daemon_tick"}`, после чего цикл
запускается заново. Пауза перед повтором удваивается от 1 до 60 секунд. С `--once` ошибка
завершает команду с ненулевым кодом.

## `maintenance`

Нормализует истёкшие состояния, закрывает аренды и удаляет данные старше retention:

```bash
identity-hub maintenance
identity-hub maintenance --once
```

Постоянный процесс проверяет расписание раз в секунду. Не запускайте его вместо
`dispatcher`: у процессов разные циклы, хотя dispatcher также вызывает due-задачи.
Допустимо держать несколько экземпляров — операции хранилища конкурентно безопасны.

Как и `dispatcher`, постоянный процесс не завершается от ошибки тика: она логируется,
считается в `identity_hub_failures_total{scope="maintenance", reason="daemon_tick"}`, а
следующая попытка идёт с растущей паузой (от 1 до 60 секунд).

## `doctor`

Проверяет денормализованные регионы, факторы верификации, последовательности
событий и счётчики привязок прокси:

```bash
identity-hub doctor
identity-hub doctor --fix
```

Без `--fix` наличие расхождений даёт код возврата 1. С `--fix` найденные
расхождения исправляются и команда возвращает 0; изменения всё равно следует
проверить по журналу и метрикам.

Дополнительно `doctor` показывает строки, зашифрованные не активным мастер-ключом:
`issue: inactive-key <набор> <key_id> <число>`. `--fix` их не исправляет — это делает
`rotate-key`; пока такие строки есть, код возврата 1.

### `doctor renormalize`

Пересчитывает `normalized_ref` аккаунтов сервиса после того, как в коде изменились
`normalize_ref` и `normalize_ref_version`:

```bash
identity-hub doctor renormalize --service telegram
identity-hub doctor renormalize --service telegram --batch-size 500
```

```text
updated: 1284
collision: 0198c1f2-… 0198c1f3-…
invalid: 0198c200-…
```

- `updated: <число>` — сколько аккаунтов получили новое значение.
- `collision: <id> <id> …` — после нормализации эти аккаунты совпали бы по ref. Пачка с
  коллизией не применяется: объедините или удалите дубли и запустите команду снова.
- `invalid: <id>` — новый нормализатор отверг ref этого аккаунта.

В выводе только идентификаторы: значения ref (телефоны, email) не печатаются. Код возврата 0,
если коллизий и отказов нет, иначе 1. Команда идемпотентна: уже пересчитанные строки она не
трогает. Из кода то же даёт `await hub.doctor.renormalize(service)` → `RenormalizeReport`.

## `rotate-key`

После добавления нового KEK первым в конфигурации переоборачивает зашифрованные
DEK пакетами:

```bash
export IDENTITY_HUB_KEK='k2:<новый-base64>,k1:<старый-base64>'
identity-hub rotate-key --batch-size 500
```

Команда обходит все наборы с шифртекстом, включая незавершённые фоновые импорты
(`ih_import_items`), и печатает число переобёрнутых записей. Строки, которые держала другая
транзакция, подбираются повторными проходами. Если что-то осталось под прежним ключом,
команда печатает остаток и возвращает код 1:

```text
1284
remaining: credentials k1 2
unreadable: sessions 0198c1f2-…/default
```

- `remaining: <набор> <key_id> <число>` — строки под неактивным ключом. Причины: строку
  держит долгая транзакция, её не удалось расшифровать, либо воркер со старой конфигурацией
  продолжает писать прежним ключом (см. ниже). Запустите команду ещё раз.
- `unreadable: <набор> <первичный ключ>` — строку не удалось расшифровать: ключа нет в
  конфигурации или данные повреждены. Остальные строки пачки при этом переоборачиваются.

Старый ключ удаляйте из конфигурации только после кода возврата 0 (или пустого
`identity-hub doctor`) на всех экземплярах приложения и с учётом резервных копий, которые
должны оставаться читаемыми. Из кода то же даёт `await hub.doctor.rotate_key()` →
`RotationReport` (`counts`, `remaining`, `unreadable`, `complete`) и
`await hub.doctor.inactive_keys()`.

### Как процессы узнают о новом ключе

Провайдер читает ключи один раз, при создании. Работающий воркер продолжает шифровать
старым активным ключом, пока не получит новую конфигурацию, поэтому порядок такой:

1. Добавьте новый ключ **первым** в конфигурацию всех процессов.
2. Обновите ключи в процессах: `EnvSecretsProvider` — перезапуском; `FileSecretsProvider` —
   перезапуском или вызовом `provider.reload()` (например, по `SIGHUP` или таймеру). `reload()`
   перечитывает файл и атомарно меняет набор; при ошибке в файле остаются прежние ключи.
3. Когда все процессы шифруют новым ключом, запустите `identity-hub rotate-key`.
4. Только после этого удаляйте старый ключ из конфигурации.

### Требования к ключам

- `key_id` — от 1 до 64 символов из `A-Z`, `a-z`, `0-9`, `_`, `.`, `-`.
- Ключ — 32 случайных байта в base64; создавайте его командой
  `python -c "from identity_hub.crypto import generate_key; print(generate_key('k2'))"`.
  Ключ из одинаковых байтов отклоняется.
- BOM в начале файла игнорируется. Сообщение об ошибке формата называет номер записи и не
  содержит ни ключа, ни `key_id`.

## `rollups`

Обслуживает временные корзины аналитики (`ih_stats_rollup`). В обычной работе их ведёт
`dispatcher`; команда нужна после сбоя или ручной правки данных.

```bash
identity-hub rollups --rebuild --space production \
  --start 2026-01-01T00:00:00Z --end 2026-01-02T00:00:00Z --yes
identity-hub rollups --purge-minutes --yes
identity-hub rollups --purge-minutes --before 2026-01-01T00:00:00Z --yes
```

- `--rebuild` заново считает корзины событий диапазона по журналу `ih_events` и заменяет
  ими прежние; печатает число записанных корзин. Нужны `--space`, `--start` и `--end`.
  Диапазон расширяется до границ суток пространства. Телеметрию операций (`telemetry.*`)
  перестройка не трогает: по журналу её не восстановить.
- Диапазон старше срока хранения событий (`Retention.events`) по журналу уже не восстановить:
  команда откажет. `--force` перестроит его, **стерев** накопленную историю.
- `--purge-minutes` удаляет минутные корзины старше срока `Retention.rollup_minutes`
  (по умолчанию 48 часов) или старше `--before`; печатает число удалённых строк.

## `snapshots`

Почасовые снимки состояния парка (`ih_state_snapshots`) для графиков «сколько было аккаунтов
в каждом состоянии».

```bash
identity-hub snapshots --backfill-current
identity-hub snapshots --purge --yes
identity-hub snapshots --purge --before 2026-01-01T00:00:00Z --yes
```

- `--backfill-current` снимает текущее состояние за текущий час; историю задним числом не
  выдумывает. Печатает число записанных строк.
- `--purge` удаляет снимки старше `Retention.state_snapshots` или старше `--before`.

Время во всех командах — ISO 8601 с часовым поясом (`Z` или `+03:00`).

## Подтверждение разрушающих команд

`rollups --rebuild`, `rollups --purge-minutes` и `snapshots --purge` удаляют или перезаписывают
данные, поэтому требуют флага `--yes`. Без него команда завершается с кодом 2, не
подключаясь к базе.

## Диагностика CLI

```bash
identity-hub --version
identity-hub --help
identity-hub dispatcher --help
```

Ошибки аргументов — неизвестный флаг, время без часового пояса, отсутствующая фабрика, нет
`--yes` — возвращают код 2 через argparse. Ошибки библиотеки печатаются как
`error[<code>]: <сообщение>` и возвращают код выхода по коду ошибки:

| Код ошибки | Exit |
|---|---|
| `validation_error`, `not_found` | 2 |
| `schema_incompatible` — ревизия схемы не та, что ожидает код | 3 |
| `database_busy` — lock/statement timeout, deadlock; повторить позже | 4 |
| `secret_configuration_error`, `decryption_failed` | 5 |
| прочие | 1 |

Ещё два вида ошибок печатают только имя типа исключения — без текста, в котором мог бы
оказаться URL базы с паролем или параметры запроса, — и возвращают код 1:

| Сообщение | Когда |
|---|---|
| `error[factory_failed]: <тип>` | фабрика хаба или импорт её модуля завершились исключением, либо фабрика вернула не `IdentityHub` |
| `error[internal]: <тип>` | непредвиденная ошибка при выполнении команды (например, обрыв соединения) |

Полный текст и трассировка пишутся в лог `identity_hub` уровня `DEBUG`: включите его в
фабрике (`logging.basicConfig(level=logging.DEBUG)`), если нужна диагностика.

Бесконечные процессы должны запускаться под supervisor с корректной доставкой
SIGTERM/отмены.
