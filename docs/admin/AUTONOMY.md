# Автономная работа над Identity Hub Admin

Основной читатель этого документа: AI-агент или разработчик, который должен продолжить реализацию
после новой сессии без скрытого контекста.

## Источники правды

Используйте источники в таком порядке:

1. [`PROGRESS.md`](PROGRESS.md): текущая задача, чекпоинт, статусы и журнал сессий.
2. [`DECISIONS.md`](DECISIONS.md): решения, снимающие неоднозначности.
3. Раздел выбранной задачи в [`PLAN.md`](PLAN.md): границы и Definition of Done.
4. [`ADMIN-PAGES.md`](ADMIN-PAGES.md), [`ADMIN-STACK.md`](ADMIN-STACK.md) и
   [`FRONTEND-DESIGN-SYSTEM.md`](FRONTEND-DESIGN-SYSTEM.md): продукт, стек и интерфейс.
5. [`identity-hub-requirements.md`](../../identity-hub-requirements.md) и код библиотеки:
   доменные гарантии и фактические контракты.

Если документы расходятся с работающим кодом, не маскируйте расхождение. Добавьте решение в
`DECISIONS.md`, тест, который фиксирует выбранное поведение, и только затем меняйте код.

## Начало каждой сессии

1. Выполните:

   ```powershell
   Get-Content -Encoding UTF8 docs/admin/PROGRESS.md
   Get-Content -Encoding UTF8 docs/admin/DECISIONS.md
   git status --short
   git log --oneline -5
   python docs/admin/progress_tool.py validate
   ```

2. Если в `PROGRESS.md` есть `in_progress`, продолжите эту задачу с первого шага `[ ]`.
   Сопоставьте незакоммиченные файлы с чекпоинтом. Не удаляйте чужие изменения.
3. Если активной задачи нет, выполните `python docs/admin/progress_tool.py next`. Возьмите только
   первую доступную задачу, у которой все зависимости `done`.
4. Прочитайте весь раздел задачи в `PLAN.md`, применимые решения и реальные контракты кода.
5. Разбейте работу на 3–8 проверяемых шагов и зарегистрируйте старт:

   ```powershell
   python docs/admin/progress_tool.py start A0.1 "проверить исходные контракты" "добавить тесты" "реализовать" "запустить проверки"
   ```

## Выполнение задачи

Работайте вертикально: контракт и тесты, затем бэкенд, сгенерированный клиент, интерфейс и
сквозная проверка. Не оставляйте ручную синхронизацию типов между OpenAPI и TypeScript.

После каждого законченного шага сохраните чекпоинт:

```powershell
python docs/admin/progress_tool.py check "добавить тесты"
```

Перед потенциальным обрывом добавьте точную заметку:

```powershell
python docs/admin/progress_tool.py note "API готов; продолжить с frontend/src/pages/...; последний тест ..."
```

Заметка должна отвечать на три вопроса: что уже работает, что не закончено, какой командой увидеть
текущую проблему.

## Обязательные проверки

Набор зависит от затронутых слоёв. Команды уточняются в A0.2, но их стабильные имена сохраняются.

```powershell
# Библиотека, если изменён src/identity_hub или её миграции
bash scripts/check.sh

# Пакет админки
uv run --project admin poe check-backend

# Фронтенд
npm --prefix admin/frontend run check
npm --prefix admin/frontend run test

# Сквозные тесты и production build
uv run --project admin poe test-e2e
npm --prefix admin/frontend run build

# Проверка структуры прогресса
python docs/admin/progress_tool.py validate
```

Запускайте только применимые быстрые проверки во время разработки, но перед `done` выполните все
проверки из Definition of Done задачи. Для изменений shared-компонентов обязателен
`npm --prefix admin/frontend run test:visual`. Для миграций обязательны upgrade с предыдущей
ревизии и проверка чистого развёртывания PostgreSQL 16.

## Закрытие задачи

Задача считается завершённой, только когда:

- выполнен её Definition of Done;
- все шаги текущего чекпоинта отмечены `[x]`;
- тесты действительно запускались, а их код возврата был нулевым;
- OpenAPI и сгенерированный клиент синхронизированы, если менялся API;
- документация и решения обновлены, если изменился контракт;
- в рабочем дереве нет случайных артефактов, секретов и несвязанных изменений.

Закройте задачу и создайте локальный коммит:

```powershell
python docs/admin/progress_tool.py done A0.1 - "проверены контракты; добавлен отчёт · дальше A0.2"
git add <только файлы задачи> docs/admin/PROGRESS.md
git commit -m "chore(A0.1): зафиксировать базовые контракты"
```

`-` означает, что hash будет пустым до коммита. Его можно не заполнять: журнал и grep по ID дают
однозначную связь. Не делайте `push` и не публикуйте пакет без явного запроса.

## Ошибки, блокировки и изменение плана

- Не ослабляйте тест, типизацию, авторизацию или визуальные ограничения ради зелёной проверки.
- При безопасной неоднозначности выберите консервативный вариант, добавьте `A-D1xx` и продолжайте.
- `blocked` применяется только к внешней причине, которую нельзя устранить в репозитории. Укажите
  точную причину и способ разблокировки, затем возьмите следующую независимую задачу.
- Если задача больше одной разумной сессии, добавьте решение о разбиении, замените строку задачи на
  дочерние `A<id>a`, `A<id>b` и сохраните зависимости. Уже выполненную работу не теряйте.
- Изменение схемы Identity Hub всегда оформляйте новой Alembic-миграцией. Существующие миграции не
  редактируйте.
- Изменение публичного контракта библиотеки требует записи и в `docs/plan/DECISIONS.md`.

Команды статуса:

```powershell
python docs/admin/progress_tool.py status A2.4 blocked "ожидается публичный identity_card v2 из библиотеки"
python docs/admin/progress_tool.py status A2.4 todo "контракт добавлен, задача снова доступна"
python docs/admin/progress_tool.py summary
```

## Правила безопасности

- Никогда не помещайте реальные credentials, session, токены, KEK, пароли и webhook secrets в
  fixtures, snapshots, логи, события, URL или историю git.
- Для тестов используйте очевидно фиктивные значения и отдельные ключи.
- Не логируйте тела запросов к endpoint-ам показа секретов и импорта.
- Не обходите методы библиотеки прямым SQL из админки.
- Все мутации проверяют роль, пространство, CSRF или bearer-аутентификацию, ожидаемую ревизию и
  идемпотентность до выполнения действия.
- Любое массовое действие сначала показывает число целей и требует явного подтверждения.
