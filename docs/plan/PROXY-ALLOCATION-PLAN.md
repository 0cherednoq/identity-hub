Статус: PA0.1–PA5.2 завершены. Схема 0048, read-схема v6, inner proxy request v2.

Дата: 2026-11-24. Аудитория: разработчик и ревьюер Identity Hub.
Идентификаторы задач: `PA<фаза>.<номер>`. План не меняет приоритеты действующих очередей.
Прогресс: [PROXY-ALLOCATION-PROGRESS.md](PROXY-ALLOCATION-PROGRESS.md).

## 1. Результат и границы

Библиотека предоставляет жизненный цикл назначения прокси аккаунту:
**зарезервировать ёмкость → использовать под арендой аккаунта → подтвердить постоянную
привязку либо освободить резерв → впоследствии снять привязку**.
Решение о подтверждении принимает приложение либо декларативная политика сервиса.

Понятие «валидный аккаунт» в ядро не вводится. Подтверждение может означать успешный вход,
проверку сессии, окончание регистрации, ручное одобрение или завершение нескольких проверок.
Снятие привязки тоже имеет собственные условия. Неуспех проверки не равен подтверждённой
невалидности, а временная невозможность работы не обязательно требует смены IP.

| Потребитель | Когда подтверждает | Когда снимает привязку |
| --- | --- | --- |
| Checker | Приняты все нужные результаты проверки | Принят терминальный статус аккаунта |
| Регистрация | Создание аккаунта завершено | Аккаунт закрыт или регистрация отменена |
| Ручной onboarding | Оператор одобрил назначение | Оператор отозвал одобрение |

Все три сценария используют одно назначение и одни команды. Специальные методы
`bind_if_account_valid` и флаги `is_valid` для прокси не добавляются.

Первый выпуск включает:

- временное назначение с учётом ёмкости и защитой владельца;
- атомарное превращение резерва в постоянную привязку;
- повторное использование существующей привязки;
- явное подтверждение и правила подтверждения/отвязки по состоянию аккаунта;
- освобождение при завершении, отзыве, истечении или потере аренды;
- восстановление после падений, аудит и чтение загрузки;
- совместимость с прежним режимом через явное включение строгого учёта для группы.

В первый выпуск не входят самостоятельные аренды прокси без аккаунта, покупка прокси у провайдера,
лимиты TCP-соединений, смена IP внутри живого клиента, общий движок произвольных ресурсов,
произвольные Python callbacks в транзакции и бронирование между шагами человеческого challenge.
Строгий режим первого выпуска работает только с эксклюзивными арендами аккаунта.
Существующий `SHARED` в прежнем режиме сохраняется; поддержку `SHARED` в новом режиме выносим
в отдельное расширение с собственным контрактом TTL и учёта использований.

## 3. Разделение ответственности

### 3.1. Выбор прокси

`ProxyPolicy.group` задаёт источник кандидатов, `on_proxy_down` задаёт поведение при недоступности
существующего прокси. Группа остаётся набором адресов пространства, не становится свойством сайта.
Два сервиса могут намеренно использовать одну группу. Изоляция сайтов достигается разными группами;
политика ёмкости при этом общая для всех потребителей одной группы.

### 3.2. Владение ёмкостью

Внутренний `ProxyAllocation` представляет назначение конкретного прокси конкретному аккаунту.
Назначение занимает место независимо от того, стало ли оно постоянной привязкой.
У временного назначения есть владелец: конкретная аренда аккаунта с полным `LeaseFence`.

Единица лимита: место назначения аккаунта на прокси, а не запрос, операция или соединение.
Повышение резерва до привязки сохраняет то же место. Использование существующей привязки
не занимает второе место. Нельзя создать два оплачиваемых ёмкостью назначения одной пары
`(space_id, identity_id, proxy_id)`; повторное использование ссылается на существующее назначение.
При замене прокси старое и новое назначения могут временно занимать по месту на разных прокси.

### 3.3. Решение о постоянной привязке

Два независимых правила:

- **подтверждение**: когда временное назначение разрешено сделать постоянным;
- **снятие**: когда существующую привязку требуется отозвать.

Ложное условие подтверждения не означает, что существующую привязку нужно снять.
Неопределённый результат проверки не означает отрицательное решение.
По умолчанию постоянная привязка сохраняется до явной команды снятия.

## 4. Обязательные инварианты

| ID | Инвариант |
| --- | --- |
| PA-R01 | В строгой группе свободное место выбирается и занимается одной транзакцией |
| PA-R02 | Занятость равна `bound + reserved + draining`; подтверждение не увеличивает сумму |
| PA-R03 | Все пути назначения строгого прокси используют один механизм учёта, включая импорт и admin API |
| PA-R04 | У аккаунта не более одной действующей постоянной привязки; каждое её создание получает новый ID поколения |
| PA-R05 | Подтвердить резерв может только его живая эксклюзивная аренда с полным совпадением fence |
| PA-R06 | Резерв живёт не дольше владельца; heartbeat не продлевает его за `hold_deadline` |
| PA-R07 | Повтор acquire восстанавливает исходный proxy/allocation, а не ищет текущую привязку заново |
| PA-R08 | Освобождение, подтверждение и cleanup не списывают место дважды |
| PA-R09 | Старый verdict или команда не меняют новое поколение назначения/привязки |
| PA-R10 | Нельзя повторно выдать место, пока назначение используется действующей арендой |
| PA-R11 | Сетевой I/O выполняется вне транзакций; результат и решение по назначению фиксируются согласованно |
| PA-R12 | Правила применяются к итоговому принятому состоянию команды, с учётом `sticky`, `pinned`, `stale` |
| PA-R13 | Секреты прокси и lease token не попадают в read API, события, ошибки и repr |
| PA-R14 | Очистка восстанавливает доступность; её задержка не разрешает переполнение |
| PA-R15 | Старые группы сохраняют прежние гарантии до явного переключения режима |

«Используется» означает действующую аренду в БД. После её истечения fencing отклоняет записи,
но не может физически остановить сетевой запрос зависшего процесса. Это та же граница гарантии,
что у текущих аренд аккаунтов. Остановку клиента обеспечивает приложение через отмену/on_lost.

## 5. Жизненный цикл назначения

| Состояние | Занимает место | Есть постоянная привязка | Допустимое продолжение |
| --- | --- | --- | --- |
| `reserved` | Да | Нет | `bound`, `draining`, `released` |
| `bound` | Да | Да | `draining`, `released` |
| `draining` | Да | Нет | Только `released` |
| `released` | Нет | Нет | Терминальное состояние |

`draining` означает: решение о снятии уже принято, но текущая аренда ещё может использовать адрес.
Новые использования этого назначения запрещены. После окончания последнего использования
место освобождается. Возвращать `draining` в `bound` нельзя: новое решение создаёт новое поколение.
Пока у аккаунта есть живое draining-использование, новая аренда этого аккаунта не выдаётся.
Старая привязка не восстанавливается из позднего подтверждения прежнего владельца.

Основные переходы:

1. Нет привязки, включено отложенное подтверждение: acquire создаёт `reserved` и lease-use одной
   транзакцией. Аккаунт сразу получает `lease.proxy`, а в списке постоянных привязок записи нет.
2. Подтверждение: `reserved → bound`, создаётся `ih_bindings`, счётчики меняются `-1 reserved,
   +1 bound`. Идентификатор назначения и URL текущей аренды сохраняются.
3. Lease завершился без подтверждения: использование закрывается, `reserved → released`.
4. Lease завершился после подтверждения: использование закрывается, `bound` остаётся.
5. Снятие привязки при живом использовании: удаляется действующая привязка,
   `bound → draining`. Следующее назначение старому владельцу не подменяет URL текущего клиента.
6. Снятие без использования: `bound → released` в той же транзакции.
7. Резерв отменён политикой/администратором при живой аренде: `reserved → draining`.
   Он больше не подтверждается, но место остаётся занятым до закрытия/отзыва аренды.

Отдельного метода «освободить место и продолжать работать через этот URL» нет.
Если нужно освободить место немедленно, сначала отзывается аренда аккаунта.

### 5.1. Повторное использование и замена

При `sticky=True` пригодная существующая привязка имеет приоритет над новым резервированием.
Несовпадение её группы с новой конфигурацией само по себе её не переносит, как и сейчас.
Новая политика начинает действовать на новых назначениях; перенос делается явно.

`WAIT` сохраняет привязку недоступного прокси. Временная сетевая ошибка не снимает её.
Выключенный оператором прокси сохраняет текущую семантику запрета выдачи, включая `REBIND`.

При `REBIND` и отложенном подтверждении новый прокси сначала резервируется.
Старую привязку не удаляем до подтверждения замены. Подтверждение атомарно проверяет
`expected_binding_id`, устанавливает новую привязку и освобождает/дренирует прежнее назначение.
Неуспешная проверка нового прокси сохраняет старую привязку. Автоматический цикл смены нескольких
прокси внутри одной аренды в первый выпуск не входит.

### 5.2. Challenge и несколько шагов проверки

Неподтверждённый резерв освобождается при завершении lease, в том числе с исходом `CHALLENGED`.
Он не удерживается на всё время ожидания SMS или человека. Если приложению нужен тот же IP между
попытками, приложение явно подтверждает привязку по своей политике до завершения аренды либо
использует прежний режим немедленной привязки. Самостоятельный долгий reservation TTL сейчас
не добавляется. Это отдельная будущая задача с ограничением времени удержания и восстановлением.

## 6. Предлагаемый публичный контракт

Имена ниже проектные. При реализации их фиксируем контрактными и typing-тестами.
Примеры показывают будущий API, сейчас они не исполняются.

### 6.1. Строгий учёт включается для всей группы

```python
await space.proxies.configure_group(
    "site-a",
    capacity_accounting="allocations",
    actor="ops",
    reason="enable reserved capacity",
)
```

Минимальная сохранённая конфигурация группы: `(space_id, name, capacity_accounting, revision)`.
Это требуется для согласованности разных сервисов, пулов, импортов и процессов. Одна настройка
в локальном `Pool` не может задавать глобальный инвариант ёмкости.

- `bindings`: прежнее поведение, используется по умолчанию для совместимости.
- `allocations`: строгий учёт всех новых назначений. В этом режиме даже `sticky=False` занимает
  временное место на срок аренды; выбранный адрес по-прежнему не закрепляется автоматически.
- Отложенное подтверждение разрешено только для `allocations`; иначе ошибка конфигурации.
- Увеличивать физическую ёмкость через `ProxyPolicy.max_identities` нельзя в строгой группе.
  `None` берёт лимит прокси; явное значение может только сузить его. Значение выше лимита прокси
  отвергается. Старый режим сохраняет прежнюю семантику override.
- `max_identities` остаётся лимитом назначений. Лимит параллельных соединений не добавляется.
- Группы материализуются из имеющихся прокси миграцией; `create/ensure/create_many` создают
  отсутствующую конфигурацию с режимом `bindings`. Добавление прокси в строгую группу наследует её режим.
- Режим определяется фактическим proxy, включая повторное использование привязки из другой группы.
  Локальная политика пула не может представить строгий proxy как legacy и обойти учёт использования.
- Переключение сериализуется с выдачей. Для первого выпуска требуется остановка выдачи и отсутствие
  живых использований группы. При невозможности доказать отсутствие использований переключение
  отклоняется; нужен drain всех затрагиваемых аренд пространства, а не предположение по `bound_count`.
  После полного обновления runtime строятся назначения существующих привязок и проверяются лимиты.
- Обратное переключение запрещено при активных назначениях нового режима. Обычный rollback
  приложения не должен оставлять новые резервы невидимыми старому allocator.

### 6.2. Явное подтверждение

```python
proxy_policy = ProxyPolicy(
    group="site-a",
    sticky=True,
    binding=ProxyBindingPolicy(mode="deferred"),
)

# Внутри уже полученной подходящей аренды аккаунта:
verdict = await application_check(proxy=lease.proxy.reveal())
if verdict.accepted:
    await lease.confirm_proxy(reason="application_check_accepted")
# Без подтверждения резерв закроется вместе с lease.
```

`application_check` и `verdict` принадлежат приложению. Пример не задаёт способ выдачи provisioning
или диагностической аренды и не предлагает вложенный вызов `auth.login()` под уже захваченным lease.

`lease.confirm_proxy()` использует actor/holder и полный fence аренды, не принимает произвольный
`identity_id` или другой proxy. Повтор подтверждения того же назначения возвращает прежний результат
без второго события и списания места. Потерянная аренда не получает права мутации даже при повторе;
статус старого подтверждения можно прочитать отдельно. Подтвердить освобождённый резерв нельзя.

`lease.proxy` и `lease.proxy_id` сохраняются. Добавляются безопасные `proxy_allocation_id` и
`proxy_assignment_state`. Уже созданный `Lease` не обещает автоматически обновлять snapshot из БД.
Метод подтверждения возвращает актуальный результат назначения.

Без `binding` сохраняется немедленная sticky-привязка. `binding.mode="deferred"` требует
`sticky=True`; сочетание со `sticky=False` отвергается при нормализации. `sticky=False` в строгой
группе означает только временное использование без подтверждения. В старой группе его прежняя
семантика сохраняется. Не вводим два противоречащих друг другу способа задать один режим.

При подтверждении прокси должен оставаться включённым и пригодным. Если он успел стать
недоступным, резерв сохраняется до конца lease, подтверждение возвращает типизированный отказ.
Выбрать другой proxy в этом методе нельзя. Изменённая администратором привязка даёт конфликт поколения.

### 6.3. Автоматические правила по состоянию

```python
binding = ProxyBindingPolicy(
    mode="deferred",
    bind_when=AllOf(
        RegionIn("auth", key="default", states={"authenticated"}),
        RegionIn("standing", states={"good", "limited"}),
    ),
    unbind_when=RegionIn("standing", states={"banned", "deleted"}),
)
```

Ограниченный декларативный язык: `RegionIn`, `AllOf`, `AnyOf`. Без произвольных функций, SQL,
строковых выражений и сетевых проверок. Валидируем регион, ключ и допустимые состояния по `Service`.
Правила сериализуемы; runtime templates строят их из проверенной конфигурации.
Не вводим отдельные состояния аккаунта `valid/invalid`.

- `bind_when=None`: только явное подтверждение. Если правило задано, оно также является
  предусловием ручного `confirm_proxy`; ручной вызов не обходит правило.
- `unbind_when=None`: автоматическая отвязка выключена.
- Совпали оба правила: снятие имеет приоритет; подтверждения в этой транзакции нет.
- Решение о снятии отменяет также текущий резерв замены аккаунта: он переходит в draining,
  если используется. Нельзя снять привязку по невалидности и затем подтвердить ранее начатую замену.
- Технический сбой без принятого изменения состояния не запускает отвязку.
- `bind_when` проверяется при принятии нового результата под владельцем резерва. Уже подходящее
  состояние при acquire само по себе не подтверждает резерв до новой проверки.
- `unbind_when` проверяется по итоговому состоянию затрагиваемой команды, независимо от источника:
  probe, login, observe, override, импорт обновления, timer. Снятие не требует прав старого lease.
- Политика реагирует на зафиксированное состояние, а не на сырые вердикты провайдера.
  `pinned/sticky/stale`, не изменившие состояние, не обходятся через proxy policy.
- Составная команда согласовывается после всех своих изменений, например после сохранения сессии
  и auth. Согласование после каждого `apply_region_change()` недопустимо.
- Разные транзакции многошаговой проверки остаются разными наблюдаемыми решениями. Для требования
  «закрепить лишь после всех шагов» используем явное подтверждение в финализации приложения;
  автоматическая политика не угадывает завершение пользовательского workflow.

Встроенные `login`, `verify_session`, `adopt_session`, `revalidate` и `sync` вызывают общий механизм
до освобождения своей аренды. Нельзя советовать пользователю делать `confirm`/`unbind` после возврата
из `auth.login`: внутренний lease к этому моменту уже завершён.

### 6.4. Применение результата и подтверждение в одной транзакции

Для собственного checker нужны два уровня:

1. Самостоятельный `lease.confirm_proxy()` для решений, не записывающих другое состояние в Hub.
2. Тот же метод под транзакцией приложения через `lease.using(session)` с последующей командой
   состояния через `space.using(session)`. Адаптер реализован в PA2.2.

```python
# Сетевой вызов уже завершён; lease всё ещё принадлежит вызывающему.
async with sessions() as db, db.begin():
    bound_space = space.using(db)
    # Записать принятое наблюдение существующим API bound_space.identities.observe(...).
    # Затем подтвердить резерв в этой же транзакции:
    await lease.using(db).confirm_proxy(reason="application_check_accepted")
```

Адаптер не переносит acquire, heartbeat и release в транзакцию пользователя. Он связывает только
команду подтверждения. Commit/rollback не должен преждевременно менять поля исходного `Lease`.
Нельзя вызывать сетевые проверки внутри этой транзакции.
`confirm_proxy` видит результат предшествующих команд той же транзакции и проверяет полный fence.
Если нужна именно совместная фиксация состояния и привязки, отдельные вызовы без общей транзакции
не являются эквивалентной заменой.

`unbind` и `rebind` получают необязательный `expected_binding_id`.
Запоздалое событие/задача с ID прежней привязки получает конфликт, не снимает новую.
Без параметра остаётся явная административная команда над текущей привязкой.
В lease-bound командах ожидаемый ID поколения проверяется обязательно.

## 7. Данные и транзакции

### 7.1. Схема

Новая миграция после актуального schema head, без изменения старых миграций:

| Объект | Изменение |
| --- | --- |
| `ih_proxy_groups` | Режим учёта и revision по `(space_id, name)` |
| `ih_proxy_allocations` | `id`, `space_id`, `identity_id`, `proxy_id`, `state`, owner lease, ожидаемая прежняя пара/поколение, JSON policy/fingerprint, timestamps, machine reason; вычисляемые active FK защищают живые ресурсы, released сохраняется после их удаления |
| `ih_bindings` | `allocation_id`, он же стабильный ID поколения текущей привязки в строгом режиме |
| `ih_proxies` | Отдельные `reserved_count` и `draining_count`; `bound_count` сохраняет смысл числа постоянных привязок |
| Lease/history | Долговечные proxy_id/allocation_id и JSON proxy_request конкретного use; не восстанавливать их из `get_binding()` |

У `reserved` срок берётся из авторитетной записи аренды. Второй независимый heartbeat/TTL
не создаётся. «Использование» в этом плане является логической связью через
`lease.proxy_allocation_id`, а не новой таблицей `ih_proxy_uses` или собственным lease-механизмом.
Живые использования определяются по существующим эксклюзивным lease-записям и их сроку.
История хранит выданное назначение для replay/аудита; её устаревший heartbeat не используется
как срок живой аренды. При перезаписи текущей аренды её старое назначение согласовывается
до выдачи нового. Ссылка владельца резерва использует стабильный lease ID и долговечную историю,
а не только identity ID перезаписываемой строки `ih_leases`.
Не удалять историю, пока на неё ссылается активное назначение. Lease token в назначении
не дублируется: владение проверяется по авторитетной записи аренды.

Нужны составные FK для совпадения space/identity/proxy, CHECK состояний и счётчиков, индексы
очистки по активным назначениям и владельцам, уникальность действующей пары identity/proxy.
Поколения старого режима допустимо представить nullable allocation ID до конвертации группы;
гарантию защиты по `expected_binding_id` обещаем для строгих назначений.

Источник правды: назначения и существующие записи аренд. Счётчики нужны для атомарного быстрого допуска;
они обновляются той же транзакцией и сверяются обслуживанием. Исправление счётчиков выполняется
под теми же блокировками, а не безусловной записью результата устаревшего `COUNT`.
Первый выпуск использует канонические существующие lease-записи для проверки использования;
точный join и индексы фиксируются в `PA0.1` по обоим хранилищам.

### 7.2. Общий allocator

Вместо новых прямых изменений `bound_count` в разных подсистемах вводятся внутренние команды
`reserve`, `attach_use`, `confirm`, `detach_binding`, `close_use`, `expire`.
Все принимают ожидаемое поколение и выполняются в `StoreTx`. Это модуль прокси,
не публичный универсальный `ResourceManager`.

В строгом режиме его используют acquire, импорт с proxy, rebind/rebind_many, unbind,
disable/delete с отвязкой, перенос proxy между группами, удаление identity и обслуживание.
Добавление нового пути с прямым `adjust_proxy_load()` запрещено.
Импорт явно заданной привязки считается отдельной административной командой: он не является
доказательством валидности. Для сервиса с deferred-политикой обычный импорт с принудительной
привязкой proxy отклоняется с `confirmation_required`. Аккаунт можно импортировать без proxy
и получить резерв из группы при проверке. Импорт доверенной привязки требует явного режима
с actor/reason и проходит общий учёт ёмкости. Хранилище неподтверждённых proxy hints в v1 не добавляется.

Переход proxy между режимами групп требует такого же drain, как переключение режима группы.
Административный `move` переносит proxy между группами с одинаковым режимом. Для смены режима
сначала явно переключают группу через `configure_group`; `move` не повышает shared-барьер
до exclusive внутри пользовательской транзакции или batch. Перенос занятого proxy отклоняется.
Смена адреса/credentials занятого строгого прокси отклоняется до drain: иначе проверка по старому
endpoint могла бы подтвердить назначение уже другого endpoint. Выключение/изменение здоровья
разрешено и перепроверяется при подтверждении. Физическое удаление proxy с активными uses
отклоняется, включая `delete(unbind=True)`, пока uses не закрыты/отозваны. Это явные отличия
нового строгого режима; старый режим сохраняет прежнее поведение.

### 7.3. Порядок блокировок

Сохраняем основу [`lock-order.md`](../lock-order.md), дополняем её явно:

1. Advisory-барьер конфигурации пространства: shared для обычных транзакций, exclusive для
   `configure_group` в своей транзакции (`D-338`). Конфигурация может кэшироваться внутри StoreTx.
   Этот барьер заменяет предложенные первоначально блокировки отдельных групп и исключает
   обратный захват при определении группы уже выбранного аккаунта. Обычные транзакции совместимы.
2. Ключ идемпотентности команды, если есть.
3. Все затрагиваемые identity по ID, затем существующие региональные данные.
4. Все затрагиваемые proxy по ID, затем allocation/binding в определённом порядке.
5. Lease/history, provider operation и outbox в существующем порядке.

Нельзя дописать cleanup прокси после уже взятой lease-блокировки. Release/revoke/expiry должны
быть перестроены вокруг общего порядка, включая reclaim при acquire и принудительный yield.
Sweeper сначала читает ID кандидатов без удержания lease-lock, затем в короткой транзакции
повторно проверяет владельца, срок и состояние в общем порядке. При пропуске занятой строки
обеспечить повторный обход, не постоянное голодание. Сетевого I/O в этих транзакциях нет.

### 7.4. Finalization и идемпотентность

Применение provider claim, принятого состояния, решение по назначению и outbox должны иметь
одну точку фиксации. Сохраняем существующую защиту от позднего claim и `projection_failed`.
Не вводим асинхронного подписчика, который позже меняет привязку по старому событию.
Общий hook вызывается из внешней границы проекции/команды, а не из низкоуровневого изменения поля.

Конфликт ожидаемого поколения не должен затереть административную замену. Для встроенной
проекции это типизированный результат согласования (`assignment_changed`), который сохраняется
вместе с принятым verdict; для явного `confirm_proxy` это отказ команды. Потеря fence/claim
по-прежнему отвергает поздний verdict целиком. Это разные исходы, их нельзя смешивать.

Idempotency fingerprint acquire включает нормализованную proxy policy и revision режима группы.
Изменившаяся политика при том же ключе даёт конфликт, а не новую выдачу. Для старых ключей нужен
versioned fingerprint и явная стратегия совместимости, проверенная миграционным тестом.
Повтор живого acquire возвращает сохранённое назначение, даже если текущая привязка уже снята
или заменена. Нельзя возвращать URL другого прокси под старым lease ID.

### 7.5. Изменение политики и времени

Версия/отпечаток нормализованной политики сохраняется в назначении. Пулы могут менять выбор
группы и ужесточать подтверждение, но не обходить правила сервиса или глобальный учёт ёмкости.
Сервисный deferred-режим нельзя заменить немедленной привязкой на уровне пула; сервисное
`bind_when` остаётся обязательным предусловием, а `unbind_when` сервиса не отключается пулом.
Ужесточение выполняется композицией правил, а не заменой всего объекта `ProxyPolicy`.
Неизвестная версия политики отклоняет мутацию, а не применяет молча другую конфигурацию.
Runtime service revision перепроверяется при finalization; изменение правил во время проверки
даёт `policy_changed` и требует новой попытки подтверждения под актуальной политикой.
Статические сервисы требуют согласованного deploy процессов; произвольное расхождение их кода
не покрывается гарантиями одной конфигурации БД.

Смена правил не запускает массовую отвязку сама по себе. Для старых привязок нужна явная
пакетная reconcile-команда с текущей revision и обычным аудитом. Изменение режима группы не
подменяет изменение бизнес-политики сервиса.
Зависимость правил от времени в v1 ограничена уже существующими переходами timer. Произвольные
условия «старше N минут» и собственный планировщик выражений не добавляются.

## 8. Восстановление и наблюдаемость

Нормальное завершение, revoke, forced yield, max_hold и expiry закрывают use через один внутренний
путь. Он идемпотентен и не трогает назначения нового поколения.
При подтверждённой привязке закрытие use сохраняет binding; при reserved/draining освобождает место.

Maintenance обрабатывает ограниченные пачки orphan/expired uses и сверяет счётчики. Acquire может
лениво очистить истёкшие назначения выбранного proxy в ограниченном объёме. Если лимит очистки
исчерпан, допустим временный отказ выдачи; недопустимо игнорировать неочищенную занятость.
Cleanup нужен и для `bound` с потерянным use, чтобы история и диагностическое чтение не зависали.
`released`-назначения удаляются только после срока хранения идемпотентности/истории и исчезновения
ссылок. Очистка не должна делать старое подтверждение похожим на новый неизвестный резерв.
Для аудита после удаления достаточно сохранённых событий с ID поколения.

Read API разделяет `bound_count`, `reserved_count`, `draining_count`, `occupied_count`, доступную
ёмкость и режим группы. `occupied_count` считает консервативно занятые места; отдельно доступно
число ожидающих cleanup. Старое поле `bound_count` не получает нового скрытого смысла.
`hub.read.proxy_bindings` продолжает показывать только постоянные привязки. Новые назначения
выносятся в отдельный selectable с обновлением версии read-схемы.

Новые события: `proxy.reservation.created`, `proxy.reservation.confirmed`,
`proxy.reservation.released`, `proxy.allocation.draining`, `proxy.allocation.released`.
Существующее `proxy.binding.changed` сохраняется только для изменения постоянной пары.
Два события одной команды допустимы, повтор команды не создаёт повторных событий.
В событиях: allocation/binding ID, proxy ID, identity ID, lease ID, причина, policy revision.
URL с credentials, lease token и необработанные исключения не публикуются.

Метрики: занятые места по состоянию, отказы `no_proxy`, `policy_changed`, `assignment_changed`,
длительность резерва, число истечений и задержка очистки. Не использовать identity ID как label.

## 9. Этапы реализации

Актуальные статусы задач ведутся в [файле прогресса](PROXY-ALLOCATION-PROGRESS.md).
Каждая задача включает код обоих Store, необходимые тесты и документацию контракта.

| Задача | Зависимости | Работа | Критерий завершения |
| --- | --- | --- | --- |
| PA0.1 | Нет | Зафиксировать ADR: состояния, group accounting, exclusive-only, schema/joins, lock order, fingerprint compatibility | Разобраны гонки из раздела 10; нет неуказанного владельца TTL или обхода allocator |
| PA0.2 | PA0.1 | Типы политики, нормализация, правила регионов, ошибки, публичные typing-контракты | Все несовместимые комбинации отвергаются; runtime config валидируется без callbacks |
| PA1.1 | PA0.1 | Новая схема, backfill групп, связь allocation/lease/binding, read-schema revision | Upgrade с существующими привязками и ключами; старый режим не меняет поведения |
| PA1.2 | PA0.2, PA1.1 | Общий allocator и configure_group в обоих Store | Конкуренты за последнее место дают одного победителя; rollback не оставляет счётчиков |
| PA1.3 | PA1.2 | Провести rebind/unbind, импорт, batch/admin, move/delete/update через allocator | Ни один путь строгой группы не обходит занятость и поколения |
| PA2.1 | PA1.3 | Acquire, existing binding, deferred/temporary use, replay | Reservation и lease атомарны; replay возвращает тот же proxy/allocation |
| PA2.2 | PA2.1 | confirm_proxy, lease.using(session), expected_binding_id | Совместный rollback verdict/confirm; повтор не списывает второе место |
| PA2.3 | PA2.1 | Release, revoke, expiry, max_hold, reclaim, forced yield, draining | Ни утечек мест после cleanup, ни ранней повторной выдачи |
| PA3.1 | PA2.2, PA2.3 | Общая точка finalization в login/verify/adopt/revalidate/sync и командах состояния | Запись verdict и решения назначения согласованна; поздний claim отклонён |
| PA3.2 | PA3.1 | Автоматические bind_when/unbind_when, runtime revision, reconcile существующих привязок | Отказ проекции и промежуточные поля не обходят правила; политика меняется явно |
| PA4.1 | PA2.3 | Bounded cleanup, lazy recovery, сверка счётчиков | После kill/expiry места возвращаются; sweep не блокирует выдачу длинной транзакцией |
| PA4.2 | PA3.2, PA4.1 | Read/admin DTO, события, метрики | Наблюдаемость разделяет binding/reservation/draining; секреты отсутствуют |
| PA5.1 | PA4.2 | Compatibility, race/load/migration-наборы и аудит путей | Все требования PA-R01–PA-R15 подтверждены проверками |
| PA5.2 | PA5.1 | Руководство, API reference, rollout, CHANGELOG | Потребитель реализует исходный сценарий публичным API; ограничения описаны |

После `PA2.3` доступен механизм ручного подтверждения, но фича не считается завершённой без
встроенной finalization, восстановления и миграционного пути. Публикация пакета в этот план не входит.

## 10. Проверки и матрица гонок

Общий conformance-набор запускается на MemoryStore и PostgreSQL. Конкурентность дополнительно
проверяется реальными PostgreSQL-сессиями с барьерами, а не задержками `sleep`.

| Сценарий | Ожидаемый результат | Требования |
| --- | --- | --- |
| Два аккаунта одновременно резервируют последнее место | Одно назначение; второй получает отказ/ожидание | R01–R03 |
| Reserve против rebind, import, create_many с proxy | Единый лимит без обхода через иной API | R01–R03 |
| Подтверждение резерва при полностью занятом proxy | Успех без дополнительного места | R02, R08 |
| Повтор confirm/release/cleanup | Один переход и один набор событий | R08 |
| Rollback после изменения любого счётчика | Назначение, binding, use и счётчики откатились вместе | R02, R11 |
| Confirm против revoke/expiry/max_hold | Победитель сериализации определяет результат; поздний владелец отвергнут | R05, R06 |
| Продление против sweeper на границе TTL | Продлённая аренда не очищена; истёкшая не воскресла | R05, R06, R14 |
| Unbind при работающем клиенте, затем acquire другого аккаунта | Место остаётся draining до конца использования | R10 |
| Старый unbind/провайдерный verdict после admin rebind | Новое поколение не затронуто | R04, R09 |
| Повтор acquire после изменения binding | Тот же выданный proxy; не новая текущая привязка | R07 |
| Повтор acquire с тем же ключом и другой policy/revision | Типизированный конфликт, без второй аренды | R07 |
| Rebind с deferred, проверка неуспешна | Новый резерв очищен, прежняя привязка сохранена | R04, R08 |
| Kill после reserve / до confirm / после commit confirm | Резерв истечёт; подтверждённая привязка сохранится | R06, R08, R14 |
| Pin/sticky/stale отвергли состояние; разные поля команды | Решение по принятому итоговому снимку, без промежуточного bind | R11, R12 |
| Технический сбой, challenge, invalid session при пригодных credentials | Нет встроенного заключения «аккаунт мёртв»; действует заданная политика | R12 |
| Изменение proxy endpoint/credentials или delete при use | Отказ до drain; не подтверждается другой endpoint | R09, R10 |
| Изменение runtime policy во время сетевого вызова | `policy_changed`, никакого молчаливого применения другой версии | R09, R12 |
| strict configure_group против acquire/move/import | Барьер группы, переключение только после drain | R03, R15 |
| SHARED-пул пытается получить strict proxy | Ранний типизированный отказ, без резерва | R05, R15 |
| Смена счётчиков во время reconciliation | Нет записи устаревшего COUNT поверх новой выдачи | R02, R14 |
| Другая space, подделанный fence, раскрытие secret | Отказ; в ошибках и событиях нет secret/token | R05, R13 |
| Старые группы и режимы | Существующие conformance/PG-контракты сохраняются | R15 |

Для нагрузочного теста сравнить одинаковую базу до/после: acquire/release/heartbeat, высокая
занятость группы, накопленные истечения, drain и размер пачек очистки. Измерять p50/p95,
число SQL round trips, блокировки и размер индексов. Численные бюджеты зафиксировать по baseline
до оптимизации; не заявлять заранее не измеренные гарантии.
Heartbeat не должен получать по отдельному SQL на каждую резервацию.

## 11. Переход и документация потребителя

1. Установить новый runtime во все процессы, выполнить новую миграцию. Новые группы по умолчанию
   ещё работают в прежнем режиме. Запуск старого runtime после включения strict запрещён версионным
   барьером; формальное наличие новой схемы само по себе этого не обеспечивает.
2. Проверить возможности реального version guard в репозитории. Если старый бинарник нельзя
   заставить отказаться от записи, поддерживается только coordinated rollout: остановка всех старых
   процессов, обновление и drain перед strict. Rolling-сосуществование с ними не обещаем.
3. Остановить выдачу целевой группы, дождаться всех её аренд; при неполной исторической
   атрибуции прокси дождаться всех затрагиваемых аренд пространства. Сверить существующие привязки,
   включить `capacity_accounting="allocations"` под барьером. Переполненные legacy proxy сначала
   привести к физическому лимиту; миграция не удаляет чужие привязки автоматически.
4. Настроить deferred policy в сервисе. Для типичного checker: подтвердить после принятого
   успешного результата; снимать по выбранным терминальным состояниям. Если invalid session
   считается основанием снятия, это явное правило приложения, а не общий default.
5. Возобновить выдачу и проверить чтение bound/reserved/draining, expiry и отказы ёмкости.

Обновить `docs/guide/02-services.md`, `07-leases.md`, `09-proxies.md`, `10-events.md`, `api.md`,
`limitations.md`, `docs/integrations.md` и `docs/lock-order.md`; публичные exports/typing-тесты,
схему событий, schema head/read version и CHANGELOG.
Примеры должны покрывать встроенный authenticator, ручную проверку под lease, атомарную запись
результата и confirm, неизвестный verdict, challenge и последующую отвязку. Все исполняемые
примеры проверяются на установленном публичном API без `_tx` и прямых записей в таблицы Hub.

Готовность фичи: сценарий работает при конкурентной выдаче и падении checker; решения о
валидности остаются у приложения; ни один путь выдачи строгой группы не обходит общий учёт;
старые группы сохраняют прежний контракт; ограничение exclusive-only и переход между версиями
описаны и проверены. Команды общей проверки реализации: `scripts/check.sh` и отдельные
PostgreSQL race/load-наборы по принятому протоколу репозитория.
