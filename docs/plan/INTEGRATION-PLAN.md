# Identity Hub — план доработок по итогам встраивания

Источник требований: [`ISSUES-INTEGRATION.md`](ISSUES-INTEGRATION.md) — задачи 1–7.
Прогресс: [`INTEGRATION-PROGRESS.md`](INTEGRATION-PROGRESS.md).
Решения: [`DECISIONS.md`](DECISIONS.md) (`D-221`).
Протокол автономной работы: [`CLAUDE.md`](../../CLAUDE.md).

Этот файл — спецификация задач `N<фаза>.<номер>`. Статусы ведутся только в
`INTEGRATION-PROGRESS.md`. Изменение scope, разбиение или отмена задачи оформляются записью
`D-NNN`, затем синхронно отражаются в плане, матрице трассировки (раздел 7) и прогрессе.

## Границы

- **Задача 8 (сессии-файлы больше 512 KiB) не выполняется** (`D-221`). Предел `IMP-16` остаётся,
  браузерные профили покрывает `IMP-22`.
- Очередь `N` идёт **после** очереди `I`: она меняет те же файлы аренды и хранилища
  (`lease.py`, `pool.py`, `store/base.py`, `postgres/store.py`, `testing/memory.py`).
- Квоты не меняются: фиксированное окно и списание отдельной транзакцией остаются (`G-2.1`,
  `G-2.4`). Троттлинг — отдельный инструмент рядом.

## Откуда взяты решения

Каждое решение повторяет проверенный механизм, а не изобретается заново.

| Задача | Образец | Что взято |
|---|---|---|
| Запрос уступить | Temporal: отмена активности приходит на heartbeat | флаг в ответе продления, держатель останавливается сам |
| Срок на уступку | Slurm `GraceTime`, Kubernetes grace period | необязательный `yield_grace`, после него — `revoke` |
| Выбор жертвы и бронь | Kubernetes preemption, `nominatedNodeName` | одна жертва с наименьшим приоритетом; бронь для запросившего |
| Резерв | PostgreSQL 16 `reserved_connections` | резерв задаётся в определении пула, а не на каждом вызове |
| Потолок удержания | Vault `max_ttl`, Azure `MaxAutoLockRenewalDuration` | продление не выходит за дедлайн; причина названа явно |
| Квоты при выборе | LiteLLM Router, pre-call checks | исчерпанные отсекаются до выдачи |
| Троттлинг | GCRA (Stripe, Shopify) | одна метка времени на ключ вместо журнала окна |
| Назначение аренды | метки и аннотации Kubernetes | `purpose` для группировки, `ref` для ссылки |
| Ручное продление | SQS `ChangeMessageVisibility`, Service Bus `RenewLock` | явный `renew` |

## Фаза N0 — основа

### N0.1 Контракт продления и причина отказа

Задачи 1, 4, 5 упираются в одно: продление возвращает только `datetime | None`, а
`LeaseUnavailable` не говорит, почему отказано.

- `LeaseRenewal` (frozen dataclass в `store/base.py`): `expires_at: datetime | None`,
  `end_reason: LeaseEndReason | None`. Его возвращают `StoreTx.extend_lease` и
  `Store.renew_leases`; `HeartbeatBatcher` отдаёт его во future. Следующие задачи добавляют поля
  (`hold_deadline`, `yield_requested`).
- Если аренда исчезла, `end_reason` берётся из истории по `token` в том же запросе. `_mark_lost`
  получает причину из ответа; сейчас любое исчезновение считается `revoked`.
- `LeaseUnavailableReason`: `busy` (все допустимые заняты), `no_candidates` (допустимых нет по
  состоянию или фильтру). `LeaseUnavailable.reason` и поле в `context` ошибки. Значения `reserve`
  и `quota` добавят `N3.1` и `N1.3`.
- `retry_after` для `busy` остаётся `None`, если хранилище не знает срока.
- `tests/test_integration_traceability.py`: множества задач этого плана, матрицы раздела 7 и
  прогресса совпадают; каждая задача 1–7 из `ISSUES-INTEGRATION.md` есть в матрице.
- **DoD:** conformance на обоих бэкендах: отозванная, истёкшая и освобождённая аренда дают разные
  `end_reason`; `busy` и `no_candidates` различаются; доля HOT-обновлений из `I2.2a` не упала;
  lifecycle-тесты ×3.

## Фаза N1 — поля аренды и выборка

### N1.1 Назначение аренды

Задача 6.

- `pool.lease(purpose=..., ref=...)`, то же у `pool.acquire()`; `pools.define(purpose=...)` задаёт
  значение по умолчанию.
- `purpose` — метка для группировки: 1–64 символа, `[a-z0-9_.:-]`. `ref` — свободная ссылка до
  256 символов, по ней не группируют. Оба значения проходят `sanitize_text`; нарушение формата —
  `ValidationFailed` до транзакции.
- Колонки `purpose`, `ref` (nullable) в `ih_leases` и `ih_lease_history`. Поля в `LeaseRow`,
  `LeaseHistoryRow`, `LeaseReadRow`, `READ_TABLES`; события аренды несут оба поля.
- `lease_dashboard(group_by="purpose")`.
- В отпечаток идемпотентности аренды поля не входят: повтор с тем же ключом возвращает исходные
  значения.
- `SHARED`: поддерживается (поля пишутся в историю).
- **DoD:** поля видны в `hub.read.leases`, `hub.read.lease_history`, событиях и админке; версия
  read-схемы повышена; слишком длинное и недопустимое значение отклоняются.

### N1.2 Потолок удержания аренды

Задача 4.

- `pools.define(max_hold=timedelta)` и `pool.lease(max_hold=...)`, то же у `acquire()`.
  По умолчанию `None` — прежнее поведение.
- Колонка `hold_deadline` в `ih_leases` и `ih_lease_history` (для `SHARED` продление идёт по
  истории). При захвате `expires_at = least(now + ttl, hold_deadline)`.
- Одиночное и пакетное продление: `expires_at = least(hold_deadline, greatest(expires_at, now + ttl))`.
  Пакет учитывает дедлайн каждой строки, группировка пачек по `ttl` не меняется.
- `LeaseEndReason.MAX_HOLD`, CHECK `end_reason` обновлён миграцией. `expire_leases` пишет
  `max_hold`, если аренда истекла на своём дедлайне.
- `lease.hold_deadline` доступен держателю (берётся из строки аренды, в ответе продления не
  дублируется). Держатель получает `LeaseLost` с причиной `max_hold` за `safety_margin` до
  дедлайна; поэтому `max_hold` обязан быть больше `safety_margin`.
- Событие `lease.expired` несёт причину; дедлайн есть в read-схеме и списке живых аренд.
- **DoD:** продление никогда не ставит `expires_at` позже дедлайна (оба пути, оба бэкенда);
  в пачке из аренд с разными дедлайнами каждая обрезана по своему; `max_hold < ttl` работает;
  тесты со временем ×3.

### N1.3 Учёт квот при выборе аккаунта

Задача 5. Паузы и cooling выборка уже отсекает — меняются только квоты.

- `pool.lease(for_operation="send", require_quota=True)`; без `for_operation` — `ValidationFailed`.
- В запрос кандидата передаются окна операции `(kind, window_seconds, origin, limit)` из
  `OperationRule.quotas`. Выборка получает по одному `NOT EXISTS` на окно: строка
  `ih_quota_usage` текущего окна (`date_bin`) с `used >= limit`. Поиск идёт по первичному ключу.
- Отказ: если без фильтра квот кандидаты есть — `LeaseUnavailable(reason=quota)` с `retry_after`
  до ближайшего открытия окна. Агрегат считается только на пути отказа.
- Pacing (`__pacing__`) в фильтр не входит.
- `SHARED`: поддерживается, но фильтр — оценка, а не резерв: параллельные держатели могут
  исчерпать окно после выдачи. Это записано в руководстве.
- Снять пункт «квоты не учитываются при выборе» из `limitations.md`; в `08-limits.md` заменить
  цикл «взять, получить `QuotaExhausted`, отпустить» на `require_quota`.
- **DoD:** при исчерпанных и свободных аккаунтах выдаётся свободный; при всех исчерпанных —
  `quota` и верный `retry_after`; `EXPLAIN` по-прежнему использует `ix_ih_identities_pick`;
  замер `I2.1` на 100k с половиной исчерпанных — p95 выборки ≤ 5 мс; без параметра SQL прежний.

## Фаза N2 — пробелы из `limitations.md`

Задача 7. Каждая задача убирает свою строку из `limitations.md` и описывает метод в главе
руководства.

### N2.1 `renew` для ручной аренды

- `await lease.renew()` возвращает новый `expires_at`. Обёртка над `_extend`: обновляет
  `_last_ok` и строку аренды, сбрасывает счётчики, если подошёл `stats_flush`, соблюдает
  `hold_deadline`.
- Потерянная аренда — `LeaseLost` с причиной из `LeaseRenewal`.
- Для аренды из `async with pool.lease()` вызов допустим и работает как внеочередной heartbeat.
- **DoD:** аренда из `acquire()` с периодическим `renew` живёт дольше `ttl`; после `revoke`
  `renew` бросает `LeaseLost`; глава `07-leases.md` и строка `limitations.md` обновлены.

### N2.2 Команды состояния и публичное наблюдение

- `space.identities.ban(id, *, reason, actor, expected_revision=None)`, `freeze(...)`,
  `cool_down(id, *, until | for_, ...)` — обёртки над `_override` и `_command`. Сопоставление
  `freeze` с регионом состояния взять из `04-states.md` и записать в `D-NNN`.
- События и проверка переходов — те же, что у `override`; поведение при живой аренде не
  меняется.
- `space.identities.observe(id, observation, *, actor, source)` — обёртка над
  `SpaceBase._observe`; `Observation` экспортируется из корня пакета. Приём вебхуков платформ
  остаётся в v2.
- **DoD:** каждая команда даёт то же состояние и события, что эквивалентный `override`;
  `observe` проходит ту же машину переходов, что наблюдение из операции; allowlist API и
  `docs/guide/api.md` обновлены.

### N2.3 Массовые изменения

- Сначала прочитать `admin/src/identity_hub_admin/api/bulk.py`: если логика уже есть, перенести
  её в ядро, а админку перевести на новый метод.
- `space.identities.update_many(target, *, add_tags, remove_tags, set_labels, lifecycle, actor)`,
  где `target` — `IdentityFilter` или список id. Одна транзакция; блокировки в порядке id
  (`I0.2b`); ревизия и событие — на каждый аккаунт.
- Защита от случайного охвата: обязательный `limit` (по умолчанию 1000); превышение —
  `ValidationFailed` без изменений.
- Результат — DTO со счётчиками изменённых и пропущенных.
- **DoD:** сбой на одном аккаунте откатывает всё; два параллельных вызова с пересекающимися
  наборами не дают взаимной блокировки (`pg`, ×3); недопустимый переход lifecycle в наборе
  отклоняет вызов целиком.

## Фаза N3 — ёмкость и приоритеты

### N3.1 Резерв ёмкости пула

Задача 2.

- `pools.define(reserve=N, reserve_strict=False)`; `pool.lease(keep_free=N)` переопределяет
  значение на один вызов.
- Выборка при `N > 0`: `LIMIT N+1 FOR UPDATE SKIP LOCKED`; захват идёт, только если вернулось
  `N+1` строк, берётся первая. Параллельный захват видит меньше строк и отказывает, поэтому
  ошибка возможна только в безопасную сторону. При `N = 0` запрос прежний.
- `reserve_strict=False`: если допустимых аккаунтов всего не больше `N`, резерв не применяется.
  `True`: отказ всегда.
- Отказ — `LeaseUnavailable(reason=reserve)`.
- `pool.capacity()` остаётся `int`. Новый `pool.capacity_detail()` возвращает
  `PoolCapacity(free, reserved, available)`.
- `SHARED`: `ValidationFailed`.
- **DoD:** `K` параллельных захватов при `N + m` свободных оставляют не меньше `N` (`pg`, ×3);
  ложный отказ под конкуренцией описан в руководстве; нестрогий режим запускает работу на малом
  парке; в `MemoryStore` поведение то же.

### N3.2a Приоритет аренды и запрос уступить в хранилище

Задача 1, часть хранилища.

- `pools.define(priority=int)` и `pool.lease(priority=...)`, по умолчанию `0`.
- Колонки в `ih_leases`: `priority`, `yield_requested_at`, `yield_requested_priority`;
  `priority` также в истории.
- `StoreTx.request_yield(query, priority) -> bool`: вызывается, когда выборка ничего не дала.
  Среди живых аренд допустимых кандидатов выбирается **одна** с приоритетом ниже `priority`:
  наименьший приоритет, затем самая ранняя `acquired_at`. Если подходящая аренда уже помечена
  запросом с приоритетом не ниже — новая жертва не выбирается.
- Флаг живёт в строке аренды и исчезает при следующем захвате аккаунта.
- `LeaseRenewal.yield_requested`; событие `lease.yield_requested` пишется один раз на запрос.
- `SHARED`: параметр `priority` — `ValidationFailed`.
- **DoD:** запрос не трогает аренды равного и более высокого приоритета; повторный запрос не
  плодит жертв; гонка «запрос уступить / release» покрыта детерминированным тестом в обоих
  порядках.

### N3.2b Вытеснение в API держателя

Задача 1, часть API.

- `lease.yield_requested` и колбэк `on_yield_requested` в `pool.lease()`. Внутри процесса запрос
  доставляется сразу через `hub._live_leases`, иначе — на ближайшем heartbeat. Аренда из
  `acquire()` узнаёт о запросе из `lease.renew()`.
- Обычное освобождение при выставленном флаге пишет `end_reason = yielded`; значение добавлено в
  `LeaseEndReason` и CHECK.
- `pools.define(yield_grace=timedelta)`, по умолчанию `None` — аренда не отбирается. Если задан:
  ожидающий при очередном опросе отзывает аренду, чей запрос старше срока. Фоновой задачи нет.
- Бронь: уступленный аккаунт на короткое время недоступен захватам с приоритетом ниже
  запросившего, чтобы его не перехватил другой фоновый ожидающий. Место хранения брони выбрать
  при реализации и записать в `D-NNN`.
- В `07-leases.md`: задержка реакции равна интервалу heartbeat; пример цикла с проверкой флага.
- **DoD:** сценарий из `ISSUES-INTEGRATION.md` (фоновый пул занят, срочный с `wait=30` получает
  аккаунт) проходит на обоих бэкендах; без `yield_grace` аренда не отбирается; с ним —
  отзывается после срока; бронь не даёт перехватить аккаунт; тесты ×3.

## Фаза N4 — троттлинг

### N4.1 Троттлинг частоты запросов

Задача 3.

- `Service(..., throttles={"api": Throttle(limit, per, burst=1)})`.
- Алгоритм — GCRA: чистая функция в `domain/`, состояние — одна метка времени (TAT) на пару
  «аккаунт, имя». Гарантия: в любом интервале длиной `per` не больше `limit + burst − 1` вызовов;
  при `burst=1` — строго `limit`. Критерий из `ISSUES-INTEGRATION.md` «не больше N» выполняется
  при значении по умолчанию.
- `await lease.throttle(name)` ждёт слот по часам хаба; `wait=False` возвращает время до слота и
  слот не занимает, а при свободном слоте занимает его и возвращает ноль. Неизвестное имя —
  `ValidationFailed`.
- Счёт в памяти держателя, без обращения к БД на вызов.
- Таблица `ih_throttle_state(identity_id, name, tat)`, PK `(identity_id, name)`, каскад при
  удалении аккаунта. Чтение — при захвате, только если у сервиса есть `throttles`. Запись — при
  освобождении: `tat = greatest(tat, excluded.tat)`.
- Ожидание прерывается с `LeaseLost`, если аренда потеряна.
- **DoD:** рандомизированный тест на `FakeClock`: гарантия держится при любой
  последовательности вызовов и через смену держателя; бюджет захвата из `I2.1` не превышен для
  сервиса с `throttles` и не изменился для сервиса без них.

### N4.2 Троттлинг: сбой держателя, `SHARED` и руководство

- Нечистое завершение (аренда истекла или потеряна без записи): следующий держатель стартует с
  `tat = max(сохранённый, конец прошлой аренды + допуск всплеска + интервал)`. Это верхняя
  граница TAT, достижимая при максимальной частоте, поэтому оценка всегда консервативна.
  Периодическая запись раз в `stats_flush` из исходного предложения не нужна.
- `SHARED`: счёт общий через БД — один атомарный `UPDATE` GCRA на вызов. Цена (запрос на вызов)
  записана в руководстве.
- В `08-limits.md` — таблица «квота или троттлинг: что когда брать».
- **DoD:** после падения держателя новый не превышает гарантию; параллельные `SHARED`-держатели
  суммарно укладываются в гарантию (`pg`, ×3); таблица выбора есть в руководстве.
