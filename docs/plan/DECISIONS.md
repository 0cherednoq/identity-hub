## Лог отклонений от плана

<!-- D-1xx: разбиение/добавление/отмена задач, найденные противоречия ТЗ, упрощения. -->

- **D-101** (P0.3): фикстуры сервисов `FAKE_TG`/`FAKE_EXCHANGE` создаются сразу в P1.4 (классов `Service` до P1.4 нет); фикстуры `hub`/`space` — в P2.1.
- **D-102** (P1.2): противоречие ТЗ §3.2 («banned → good только override/restore с причиной») и FR-9.1 («наблюдение применяется из любого состояния»). Решение: у региона есть `sticky` состояния (standing: `banned`); наблюдение не выводит из них (кроме переходов, явно разрешённых `sticky_exits`, для banned — `deleted`), а порождает `identity.state.drift`. Выход — override или команда `restore` с причиной.
- **D-103** (P1.2): `changed_at` для наблюдения = `min(observed_at, now)` (не раньше предыдущего `changed_at`), для команд/override/таймера = `now`. Так FR-9.2 (`observed_at < changed_at` → отброс) не отбрасывает наблюдения, сделанные между пробой и её обработкой.
- **D-104** (P1.2): `confirm_leaving` применяется к standing `banned`/`frozen` и proxy `quarantined`/`dead`. Availability `quarantined` не синхронизируется — выход из него только командой (проверка прошла).
- **D-105** (P1.6): `status:<v>` в строке поиска (пример ТЗ FR-11.1 `status:active`) — псевдоним: `active` = lifecycle `ready` и standing `good|limited`; иначе значение ищется в любом регионе (lifecycle/standing/auth/availability). Прочие `ключ:значение` парсер оставляет обобщёнными; при поиске ключ из `filterable_profile` сервиса идёт в `profile @>`, иначе — в `labels @>`.
- **D-106** (P1.6): при `profile_encrypted` в `search_text` попадают только фильтруемые поля профиля — иначе зашифрованные данные утекли бы в открытую колонку.
- **D-107** (P2.3): строки `ih_region_states` есть только у синхронизируемых регионов (standing `''`, auth по слоту, verification по фактору, requirement по коду). Lifecycle и availability живут только в колонках `ih_identities`; их оптимистическая блокировка — compare-and-set по текущему значению колонки. `auth_state` на аккаунте = слот `default`.
- **D-108** (P2.3): гонка изменений региона решается повтором внутри той же транзакции (READ COMMITTED видит свежий коммит при перечитывании), до 5 попыток, затем `ConcurrentModification`. Блокировки строк не берутся.
- **D-109** (P2.4): для `profile_encrypted` (FR-3.2) в схеме не было места под шифротекст. Миграция 0002 добавляет в `ih_identities` nullable-колонки `profile_key_id`, `profile_wrapped_dek`, `profile_nonce`, `profile_ciphertext` (AAD = `ih_identities|<id>|profile`).
- **D-110** (P2.4): повторный `register` (тот же `id` или `(service, external_ref)` в том же пространстве) возвращает `RegisterResult(created=False)` без изменений; `(service, external_ref)` в **другом** пространстве — `AlreadyExists` (FR-2.2). Привязка прокси при регистрации — в P5.2.
- **D-111** (P2.4): в миграциях после 0001 операции `op.add_column/alter_column/drop_column/create_index` получают `schema=op.get_context().version_table_schema` явно — они не проходят через `schema_translate_map`.
- **D-112** (P3.3): «LeaseLost внутри блока» (FR-6.3). asyncio не умеет внедрить произвольное исключение в чужую задачу, поэтому при потере аренды heartbeat вызывает `on_lost`, затем отменяет задачу-владельца блока; на выходе из `async with pool.lease()` `CancelledError` превращается в `LeaseLost` (`task.uncancel()`). Для кода без await-точек есть `lease.check()` и `lease.lost`. Дедлайн самоограждения считается от момента **отправки** последнего успешного продления.
- **D-113** (P4.1): pacing — счётчик `__pacing__` в окне `Pacing.work` без ограничения `used < limit`; операция, доводящая счётчик до N, проходит, затем availability → `paused` на случайные `pause` минут, а счётчик обнуляется. `identity.quota.exhausted` пишется операцией, израсходовавшей последнюю единицу окна — ровно раз за окно.
- **D-114** (P4.1): ключ операции (`ih_operation_keys`) захватывается в той же точке сохранения, что и списание квот: при исчерпании квоты ключ не остаётся занятым.
- **D-115** (P4.2): успешная операция не пишет строку в журнал (счётчики — в истории аренды на heartbeat); `operation.failed` пишется в транзакции обработки вины. `error_score`: вина аккаунта +`fault.weight`, успех — ×0.5 (запись только при `error_score > 0`); при `error_score ≥ Service.quarantine_threshold` availability → `quarantined`. Неизвестная ошибка (классификатор вернул None или его нет) — вина запроса, состояние не меняется. Вина прокси применяется к здоровью прокси с P5.1.
- **D-116** (P5.1): для `confirm_leaving` прокси (FR-9.4) миграция 0003 добавляет `ih_proxies.pending_observation`. Регион прокси хранится в колонках `ih_proxies` (status, status_changed_at, status_source, pinned_until, pending_observation) с compare-and-set по `status`. Политика здоровья — `ProxyHealthPolicy` в `IdentityHub(proxy_health=...)`: порог ошибок 3, базовый backoff 60 с (×2 за неудачную перепроверку, не больше 1 ч), `dead` после 5 неудачных перепроверок. Из `dead` выводит только ручная перепроверка (две успешные проверки подряд) или override.
- **D-117** (P5.2): `SKIP LOCKED` по прокси ложно сообщал «пул исчерпан» при параллельных захватах. Ёмкость прокси — счётчик `ih_proxies.bound_count` (миграция 0004), занимаемый атомарно `UPDATE … SET bound_count = bound_count + 1 WHERE bound_count < cap RETURNING` (как квоты); транзакция держит не больше одной блокировки прокси — без дедлоков. Счётчик уменьшается при перепривязке и удалении аккаунта; `identity-hub doctor` пересчитывает его по `ih_bindings`.
- **D-118** (P5.7): `ImportRecord.links` — роль → `"<service>:<external_ref>"` или просто `external_ref` того же сервиса (`external_ref` уникален только в сервисе). Прокси импорта попадает в пул `Service.proxy_policy.pool` (или `import`), аккаунт привязывается к нему sticky с учётом `bound_count`, но без проверки ёмкости (импорт — явное решение). `on_existing=update_session` перезаписывает сессии и наблюдает auth → authenticated (источник import); в отчёте такие записи — `updated`. Ошибка БД в пачке — вся пачка в `failed`, следующие пачки продолжаются (G-4.4).
- **D-119** (P8.2): `pool.capacity.low/empty` пишутся при **смене** состояния ёмкости пула (ok → low → empty и обратно), состояние хранится в объекте `Pool` (в процессе); проверка — `pool.check_capacity()` (вызывает обслуживание и захват при `LeaseUnavailable`). `worker.leases_lost` — агрегат: потери аренд копятся в `IdentityHub` по (пространство, holder) и сбрасываются одним событием на holder в `hub.flush_lease_losses()` (обслуживание, P9.1).
- **D-120** (P8.3): секреты ротации хранятся одним зашифрованным payload endpoint'а (`current`, `previous`, `previous_until`); в период перекрытия исходящий заголовок содержит два поля `v1`, а `verify_signature` принимает любое из них. Ручной повтор сбрасывает попытки доставки и одновременно включает endpoint/обнуляет серию отказов — это явное действие администратора после устранения причины.
- **D-121** (P8.4): при резервировании due-уведомления его статус временно становится `failed` с будущим `scheduled_at`. Это закрывает открытый дайджест до сетевого I/O: новое событие того же окна создаёт новый `pending` и не теряется при успешном завершении уже отправляемой сводки. После ответа статус становится `succeeded`, `failed` (ретрай) или `dead`; `retry_after` Telegram 429 имеет приоритет над общей exp+jitter-политикой.
- **D-122** (P9.1): maintenance-pump выполняет каждую группу сразу при первом тике процесса, затем по `time.monotonic()` с периодами 1 мин / 1 ч / 1 сут; сравнения сроков и retention остаются на `now()` PostgreSQL. Резервирование не держится во время доменной обработки: кандидаты выбираются коротко и применяются отдельными транзакциями. В минутную нормализацию также включены истёкшие challenge, уже предусмотренные ядром.
- **D-123** (P9.2): процессные CLI-команды получают настроенный `IdentityHub` через `--factory package.module:callable` / `IDENTITY_HUB_FACTORY`; так CLI не дублирует реестр `Service`, ключи и политики приложения. `migrate` остаётся автономным и принимает `--url`. Doctor считает `event_seq` ошибочным только если он **меньше** максимальной сохранившейся `sequence`: после retention отсутствие старых событий не доказывает завышение счётчика.
- **D-124** (P10.1): `MemoryStore` сериализует транзакции одним `asyncio.Lock` и перед входом делает глубокий снимок всех данных. Исключение восстанавливает снимок, успешный выход атомарно публикует изменения и будит in-process LISTEN. Такая модель намеренно не имитирует `SKIP LOCKED` построчно, но сохраняет контракт атомарности, fencing, квот и курсоров и делает гонки детерминированными в тестах.
- **D-125** (P10.2): pytest-плагин регистрируется entry point `pytest11`, а его публичные fixture имеют префикс `identity_hub_`, чтобы не конфликтовать с `hub`/`space` приложения. Conformance экспортируется наследуемым `StoreConformanceSuite`: сторонний адаптер переопределяет только `store_under_test`, а сценарии остаются общими с эталонными memory/pg прогонами.
- **D-126** (P10.3): под 50 конкурентными acquire PostgreSQL может вернуть кандидата по снимку JOIN до commit соседней аренды; уникальность и fencing не нарушаются, но `acquire_lease` видит уже живую строку. Такой конфликт считается внутренним optimistic race: транзакция откатывается, конфликтный identity исключается, выбор повторяется без пользовательской ошибки.
- **D-127** (P10.3, correction PERF-1): полный последовательный Docker Desktop прогон не достиг четырёх бюджетов §10.1: lease p95 3458.86 мс (цель 20), operation p95 13.01 мс (цель 10), поиск p95 121.18 мс (цель 100), import 10k 93.48 с (цель 60). До стабильного 1.0 обязательна отдельная оптимизация: атомарный candidate/acquire без каскада retry и сортировки 10k строк, один transaction round-trip для успешной operation, анализ плана trigram-поиска под общей нагрузкой, set-based/COPY fast path импорта. Load-тесты помечают эти четыре превышения `xfail` со ссылкой PERF-1; событие p95 47.43 мс бюджет выдержало. Статус: открыто.
- **D-122** (A0.1): read-модели админки становятся публичными типизированными методами библиотеки и не раскрывают `StoreTx` rows или SQL наружу. Общая revision аккаунта в этих DTO равна `IdentityRow.event_seq`; изменяющие admin-команды проверяют ожидаемое значение атомарно, а для region/data дополнительно используют их собственную version. Это позволяет backend админки соблюдать границу A-D003 и возвращать `412` без прямого доступа к таблицам.
- **D-128** (A1.3): `IdentityHub.get_space(slug)` возвращает только уже существующее пространство и не выполняет `ensure_space`. Admin backend использует этот публичный контракт для URL-space authorization, чтобы опечатка или произвольный slug не создавали tenant как побочный эффект проверки доступа.
- **D-129** (A3.4): ручная перепривязка прокси реализована публичной командой `SpaceHandle.rebind_proxy()`. Store блокирует строку аккаунта, затем атомарно занимает ёмкость только живого target-прокси через условный `UPDATE ... RETURNING`, меняет binding и освобождает прежний счётчик в одной транзакции. Это сериализует две команды для одного аккаунта и не позволяет параллельным аккаунтам превысить `max_identities`; событие хранит причину и обе стороны привязки без proxy secret.
- **D-130** (A3.5): публичная команда `SpaceHandle.update_session()` валидирует session моделью сервиса, шифрует payload до записи и сохраняет слот только с текущим fencing. Потеря fencing отменяет всю транзакцию. Событие `identity.session.updated` содержит actor, slot, имена полей и срок, но не значения; reveal по-прежнему возможен только через `reveal_secret()` с атомарным audit event.
- **D-131** (A3.6): `SpaceHandle.account_selection_snapshot()` возвращает ограниченный secret-free набор ID, revision, service и external_ref по тем же query/options, что список аккаунтов. Admin bulk фиксирует этот набор до preview и не переоценивает фильтр при execute. Узкие `record_admin_bulk()`/`record_admin_export()` пишут только actor, reason, operation/format, счётчики, snapshot ID и fingerprint фильтра; содержимое экспорта и значения строк в события не попадают.
- **D-132** (A3.8): публичные delivery-команды дополнены полным update/delete webhook endpoint, прямыми `Notifications.send_test()` / `Webhooks.send_test()` и `Notifications.retry()`. Test-send расшифровывает target только на время вызова транспорта и не создаёт delivery/не двигает event cursor. Ручной retry уведомления атомарно возвращает scoped delivery в `pending`, сбрасывает attempt/error/sent_at; webhook сохраняет семантику D-120 с повторным включением endpoint. Webhook URL отклоняет credentials, небезопасные схемы, local hostname suffixes и private/service IP literals, а HTTP допускает только явный `webhook_dev_hosts`; redirects отключены. Схема БД не меняется.
- **D-133** (A4.1): ревизия `0005` добавляет IANA `ih_spaces.timezone` (default берётся из `IdentityHub(timezone=...)`, существующие строки получают `UTC`), долговечные `ih_import_runs` и `ih_provider_operations`, а также индексы §5 для завершённых аренд и истории событий. Исходный файл импорта не хранится: нормализованные записи временно лежат в `ih_import_items` только в envelope-encrypted виде для возобновления после рестарта и должны удаляться при терминальном переходе run; таблица каскадно очищается вместе с run. Provider operation state нельзя надёжно восстановить из событий, потому что claim и истёкший claim являются фактами координации, поэтому он хранится отдельно по модели IMP-11. Завершённые import runs хранятся 90 дней, provider operations — 30 дней; активные строки retention не удаляет. Downgrade `0005 -> 0004` удаляет только новые административные таблицы/индексы и timezone, поэтому перед откатом требуется завершить или экспортировать нужные runs; доменные аккаунты, события и аренды не теряются. На Windows добавлена зависимость `tzdata`, чтобы IANA-валидация не зависела от системной базы зон.
- **D-134** (A3.7): `SpaceHandle.stage_import()` нормализует записи и присваивает отсутствующие UUID до staging, затем envelope-шифрует каждую строку с AAD `(ih_import_items, run_id, position)`. `ImportRunner` использует ограниченный claim, fencing token и повторный claim после expiry. Если процесс упал после domain commit, но до фиксации результата item, повтор находит identity по заранее назначенному UUID и засчитывает исход как `created`, не выполняя доменную запись повторно. Отмена не прерывает commit текущего claimed batch и становится терминальной на следующей границе. После terminal state item rows удаляются; долговечный отчёт ограничен 5000 created IDs и 1000 skipped/failed записей каждого вида, хранит только position, external_ref, code и усечённую safe reason. `identity.imported` связывается с `run_id`, а `admin.import.changed` не содержит source, входные поля, credentials или session. Публичные read contracts не возвращают ciphertext.
- **D-135** (A4.2): `identity.tier.reached/lost` вычисляются сравнением tiers до и после изменения effective verified factors и записываются вместе с verification transition в одной Store-транзакции. (2) Имя отклоняется, если **хотя бы один** его адрес не глобальный (а не «выбираем публичный из набора»). Имена, которые резолвятся, при создании endpoint'а не проверяются резолвом (DNS в момент записи ничего не гарантирует) — проверка идёт при каждом соединении; имя без точки отклоняется сразу. (3) С явным `WebhookPolicy.proxy` закрепление не действует: имя резолвит прокси; проверяются только литералы в URL, ограничение назначений — задача прокси. (4) `webhook_dev_hosts` освобождает хост и от проверки адреса. (5) Отступление от формулировки `F1.5` «фильтр, заменяющий `/bot<токен>/`»: фильтр на логгерах `httpx`/`httpcore` заменяет точные подстроки, объявленные на время запроса (`masked_in_logs`, `ContextVar`), — токен бота и путь+query URL вебхука; regexp по `/bot…/` не покрыл бы вебхуки и свой `api_url`. (6) `R2-S15`: `WebhookEndpoint.url` возвращает `scheme://host[:port]/***`; полный URL хранится в БД открытым текстом (шифрование потребовало бы миграции и не входит в находку). Read-модель `WebhookEndpointItem.masked_target` сохраняет прежний формат `…/…` — это контракт админки.
- **D-156** (F1.6, разбиение): задача `F1.6` разделена на `F1.6a` (секреты вне аренды, аудит `proxies.url` и `secrets.reveal`, `repr` — находки `R2-S05`, `R2-S10`, `R2-S14`, `R2-F19`) и `F1.6b` (приватные `store`, `envelope` и служебные объекты хаба, публичный контракт в `docs/guide/api.md`, перевод `admin/` на публичные методы — `R1-29` и остаток `R2-S10`). Причина: приватизация атрибутов хаба — механическая правка более чем 250 обращений в `src`, `admin` и тестах, не связанная с остальными пунктами. `F1.6b` зависит от `F1.6a`; `F6.4` теперь зависит от `F1.6b`.
- **D-157** (F1.6a, по умолчанию): секреты и аренда. (1) Проверка освобождения встроена в `Lease.check()`, поэтому `LeaseLost` после `release()` получают и `lease.operation()`, `mark_authenticated()`, `verification()`. (2) Чтение `credentials()`/`session()` сверяет `current_fencing` в транзакции чтения без блокировки и бросает `LeaseOwnershipLost` (подкласс `LeaseLost`): отзыв и эксклюзивный перехват увеличивают fencing, поэтому видны до heartbeat; строгий fence с блокировкой — `I2.3`. (3) `save_session()` устаревшей аренды по-прежнему бросает `StaleFencing` (контракт `G-1.4`), а не `LeaseLost`; после освобождения — `LeaseLost`. (4) `Lease.proxy` — `SecretValue`; `LoginContext.proxy_url` и `ProbeContext.proxy_url` остаются строкой: это аргумент сетевого клиента адаптера, а имя поля прямо говорит об URL. (5) Раскрытие URL прокси — новое внешнее событие `proxy.secret.revealed` (`warning`, группа `proxy`), а не `identity.secret.revealed`: у прокси нет identity. (6) `actor` и `reason` аудируемых раскрытий сохраняются без краевых пробелов.
- **D-158** (F1.6b, по умолчанию): публичный контракт `IdentityHub`. Публичны: `start`, `register_service`, `service`, `services`, `space`, `get_space`, `list_spaces`, `spaces_matrix`, `service_catalog`, `background_snapshot`, `read`, `events`, `dispatcher`, `maintenance`, `doctor`, `metrics`, `lease_log_sink`, `flush_lease_losses` и настройки только для чтения `clock`, `retention`, `timezone`, `admin_base_url`, `db_schema`, `proxy_health`, `strict_events`, `redact_refs_in_events`, `webhook_dev_hosts`, `webhook_policy`, `sessionmaker`. Приватны (с `_`): `store`, `envelope`, `import_runner`, `metric_rollups`, `rollups`, `state_snapshots`, а также не названные в `F1.6b` `webhook_dispatcher`, `notification_dispatcher`, `metrics_reporter` — это такие же служебные объекты, и через `webhook_dispatcher` доступна подмена резолвера. - **D-159** (F1.7, по умолчанию): провайдеры ключей. (1) Сообщения `parse_keys` называют номер записи, а не `key_id`: при перепутанном порядке на месте идентификатора стоит сам ключ. (2) Проверка «ключ из одинаковых байтов» действует в `parse_keys` (`EnvSecretsProvider`, `FileSecretsProvider`), но не в `StaticSecretsProvider`: туда ключи передаёт код, и тесты библиотеки и приложений используют `b"\x01" * 32`. Алфавит и длина `key_id` проверяются в обоих путях. (3) `copy`/`deepcopy` провайдера возвращают тот же объект, чтобы ключи не размножались; `pickle` — `TypeError`. (4) `FileSecretsProvider.reload()` при любой ошибке оставляет прежний набор; ошибка чтения файла — `ValidationFailed` без пути и текста ошибки ОС. Автоматического слежения за файлом нет: момент перечитывания выбирает приложение.

# D-128 — Явные административные login и verification команды

Админка вызывает выбранный аккаунт через `SpaceHandle.run_login()` и ручное решение фактора через
`SpaceHandle.review_verification()`. Методы сохраняют аренду, fencing, доменную машину переходов и
шифрование challenge внутри библиотеки; backend не читает таблицы и не расшифровывает evidence.
Причина ручного решения попадает в событие региона. Challenge answer используется только как
транзитное значение запроса и в идемпотентности представлен SHA-256 fingerprint.
