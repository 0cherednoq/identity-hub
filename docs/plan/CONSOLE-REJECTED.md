# Запросы пульта, которые не выполняются или выполняются иначе

Источник: [`../isue/ISSUES-identity-hub.md`](../isue/ISSUES-identity-hub.md). Сверка с кодом
`1.0.0a1`, ревизия схемы `0025`. Принятые пункты — в [`CONSOLE-PLAN.md`](CONSOLE-PLAN.md),
решение — `D-224` в [`DECISIONS.md`](DECISIONS.md).

Три раздела: утверждения ишью, которые не подтвердились; требования, отклонённые целиком;
требования, принятые в другой форме.

## 1. Утверждения, которые не подтвердились

| Пункт | Утверждение | Что в коде |
|---|---|---|
| 2 | «`bound_count` есть только в `proxies.list()`» | Колонка есть в публичной read-схеме: `hub.read.proxies.c.bound_count` (`postgres/read_schema.py`). Колонку «Аккаунтов» пульт может считать уже сейчас, без таблицы привязок. |
| 4 | «Одно „ядовитое“ событие повторяет всю пачку бесконечно», обойти нельзя | Повтор при исключении есть, но обработчик пачки может вернуть число обработанных событий (`BatchHandler` → `int`), и курсор встанет за ними. Изолировать сбойное событие можно на стороне потребителя. Удобный API всё равно нужен — `C4.1`. |
| 6 | «Пространство нужно создавать явно» как препятствие | Есть `hub.spaces.ensure(slug)` и `hub.space(slug, create=True)` — одна строка при старте. Отсутствие автосоздания намеренное: опечатка в имени не должна создавать пустое пространство (`R1-07`). |
| 6 | «Мы выводим ключ из `SECRET_KEY` своим кодом», потому что генератора нет | `identity_hub.crypto.generate_key()` есть и описан в README, раздел о мастер-ключе. Вывод ключа шифрования из `SECRET_KEY` приложения — решение пульта, а не ограничение библиотеки; так делать не стоит: смена `SECRET_KEY` сделает секреты нечитаемыми. |
| 6 | «В Alembic нужно вручную подключить `exclude_identity_hub`», готовой функции нет | Функция готова: `identity_hub.alembic.exclude_identity_hub`, подключается одной строкой `include_object=`. Не хватает только упоминания в «Быстром старте» — `C6.2`. |

## 2. Отклонено целиком

### Пункт 10. Карточка одним вызовом

`identities.card()` и `secrets.describe()` — два чтения, обходного решения в пульте не
требуется. Объединение смешало бы в одном ответе состояние аккаунта и сведения о секретах,
у которых разные неймспейсы и разный аудит. Вернуться к пункту стоит, если появится
измеренная проблема с задержкой карточки.

### Пункт 11. Подписи состояний в пакете

Подписи для людей — слой представления. Словарь в ядре означал бы поддержку переводов и
согласование формулировок с каждым приложением; свои формулировки приложение всё равно
переопределит. Машинные значения стабильны и перечислены в `enums.py` и `04-states.md` —
этого достаточно, чтобы словарь на стороне приложения не устаревал незаметно.

### Пункт 12. Протокол `SessionLike`

Причина на стороне пульта, это сказано в самом пункте: его слой `infrastructure` не
импортирует SQLAlchemy. `space.using()` уже типизирован (`AsyncSession` → `Self`). Тип не
теряется, если импортировать `AsyncSession` и `SpaceHandle` под `if TYPE_CHECKING:` — импорта
во время выполнения при этом нет. Протокол в публичном API стал бы вторым описанием того же
контракта, которое пришлось бы держать в соответствии с SQLAlchemy.

### Пункт 14. `actor` в `data` событий

Дублирование подтверждено (`domain/regions.py`), но удаление поля — несовместимое изменение
состава события. На `data.actor` могут опираться фильтры вебхуков (`filter={"data.…"}`) и
шаблоны уведомлений уже установленных систем. Выигрыш — одна строка в коде переноса журнала.

### Пункт 6. Схема БД по умолчанию `identity_hub`

Таблицы библиотеки имеют префикс `ih_` и не пересекаются с таблицами приложения;
`exclude_identity_hub` отбирает их по этому префиксу. Смена умолчания потребовала бы права
`CREATE SCHEMA` там, где сейчас достаточно прав на существующую схему, и изменила бы
поведение установок, которые `db_schema` не задают. Рекомендация задавать `db_schema` явно
попадает в «Быстрый старт» (`C6.2`).

### Пункт 6. `default_space` и `hub.space()` без аргумента

Экономит один аргумент ценой второго способа получить пространство и неявного создания при
старте. Константа с именем пространства на стороне приложения решает задачу без изменений в
библиотеке.

### Пункт 6. Блокировка миграции, совместимая с PgBouncer

`pg_advisory_xact_lock` не подходит: каждая ревизия фиксируется отдельной транзакцией, чтобы
сбой откатывал только её, а блокировка на транзакцию между ревизиями снималась бы.
Таблица-замок потребовала бы срока жизни, продления и снятия после сбоя — отдельный механизм
ради сценария, который принято решать иначе: миграции идут по прямому адресу, минуя PgBouncer.
Вместо блокировки — отдельный адрес для миграций (`C6.2`).

## 3. Принято в другой форме

| Пункт | Запрошено | Сделано иначе | Почему |
|---|---|---|---|
| 1 | Статус `disabled` у прокси | Флаг `enabled` с причиной и автором (`C1.4`) | Статус — наблюдаемое здоровье, выключение — намерение оператора. Четвёртый статус в машине состояний потерял бы здоровье прокси на момент выключения: после включения было бы неизвестно, жив он или в карантине. Привязки при выключении сохраняются (`D-224`, п. 9). |
| 1 | `replace_credentials_many` | Не делается; есть `update` (`C1.3`) | Массовой смены логинов в сценариях ишью нет; при необходимости добавляется на `BatchResult` без изменения контракта. |
| 3 | Отдельный набор `*_many` со своим форматом отчёта | Общий `BatchResult` с режимом `atomic` (`C0.2`), тот же для прокси и для `N2.3` | Один контракт вместо трёх разных стилей пакетных команд в одном API. |
| 4 | Типизированные payload событий (dataclass на тип) | Описанный и проверяемый тестом состав `data` (`C4.3`) | Ишью допускает этот вариант («или хотя бы описанный состав»). Класс на каждый тип события — большая поверхность публичного API, которую нельзя менять без периода совместимости. |
| 5 | `imports.run(..., session=...)` | Хук `on_batch` внутри транзакции пачки (`C5.1`) | Ишью допускает оба варианта. Импорт в сессии вызывающего держал бы одну транзакцию на весь файл: блокировки на всё время импорта и откат всех пачек при сбое последней. |
| 6 | `migrate="auto"` по умолчанию | Параметр есть, по умолчанию `"check"` (`C6.1`) | Автоприменение DDL при старте нескольких воркеров и при развёртывании с двумя версиями кода опасно; роли приложения часто не дают прав на DDL. |
| 6 | `identity-hub keygen` из-за отсутствия генератора | Команда добавляется как обёртка над существующим `generate_key()` (`C6.2`) | Генератор есть; команда — удобство. |
