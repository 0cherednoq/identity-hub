# Переход с `1.0.0a1` на текущую альфу

Документ описывает обновление установки, которая работает на схеме ревизии `0007`
(выпуск `1.0.0a1`), до текущей головы `0039`. Если ревизия базы новее `0007`, пропустите шаги,
которые её не касаются: порядок остальных не меняется. Общее правило выката без простоя и
смысл `SCHEMA_COMPATIBLE` — в [интеграции](integrations.md#обновление-без-простоя).

## 1. Preflight: что проверить до миграции

```bash
identity-hub doctor          # отчёт без изменений данных; код возврата 1 при расхождениях
```

- **Ревизия схемы.** `hub.start()` сверяет `ih_alembic_version` с `SCHEMA_COMPATIBLE` текущего
  кода и бросает `SchemaIncompatible`, если ревизия не входит в множество. Текущая голова —
  `0039`, и в `SCHEMA_COMPATIBLE` входит только она: обновление с `0007` требует остановки
  процессов, миграции и запуска нового кода.
- **Коллизии нормализации (`0008`, `D-149`).** Уникальность аккаунта считается по
  `(service, normalized_ref)`. `doctor` показывает записи, которые после нормализации
  сталкиваются друг с другом; разведите их до миграции — иначе она остановится с диагностируемой
  ошибкой, а не сольёт данные молча. Пересчёт нормализации на уже работающей базе —
  `identity-hub doctor renormalize --service <имя>`.
- **Ключи отпечатков (`0018`, `0019`, `D-207`, `D-208`).** Отпечатки прокси и ключи
  идемпотентности считаются HMAC с кольцом ключей. Кольцо задаётся явно или выводится из KEK;
  без него команды с секретами бросают `SecretConfigurationError`. Задайте ключи до запуска:
  `identity-hub keygen` печатает новый ключ, переменные окружения описаны в [CLI](cli.md).
- **Резервная копия.** Снимите дамп до `migrate`: миграции `0022`, `0023` и `0033`–`0037`
  переносят секреты и историю, и обратный переход возможен не для всех (см. §4).

## 2. Миграция

```bash
identity-hub migrate                       # или --database-url для прямого адреса
```

`migrate` берёт advisory lock на схему, поэтому одновременные запуски ждут друг друга.
Через PgBouncer в режиме транзакций используйте отдельный прямой адрес:
`IDENTITY_HUB_MIGRATE_DATABASE_URL`. В разработке допустим `IdentityHub(migrate="auto")` —
тогда миграции применяет `start()`; для нескольких воркеров это отдельный шаг развёртывания.

Что меняют ключевые ревизии на пути `0007 → 0039`:

| Ревизия | Что появилось | Решение |
|---|---|---|
| `0008` | `normalized_ref`, `normalize_version` | `D-149` |
| `0017` | `revision` аккаунта и событий | `D-205` |
| `0018`, `0019` | `fingerprint_key_id` у прокси и ключей идемпотентности | `D-207`, `D-208` |
| `0020`, `0021`, `0028` | `last_leased_at`, HOT-heartbeat, `pick_order_at` | `D-209`–`D-211` |
| `0022` | несколько `credentials` на аккаунт | `D-214` |
| `0023` | история сессий и статусы записи | `D-218` |
| `0024`, `0032` | операции провайдера и их дедупликация | `D-220`, `D-223` |
| `0033`–`0037` | открытое хранение секретов как режим хаба | `D-313`, `D-323` |
| `0038` | `verification_tier_rank` в read-схеме | `D-325` |
| `0039` | `ordered` у получателя вебхуков, поток ресурса у доставок | `D-328` |

## 3. Что изменилось в публичном API

- **Неймспейсы вместо плоских методов (`IMP-23`).** `space.identities`, `space.secrets`,
  `space.proxies`, `space.pools`, `space.imports`, `space.auth`, `space.sync`, `space.links`,
  `space.data`, `space.verifications`, `space.admin`, `space.analytics`, `space.maintenance`,
  `space.webhooks`, `space.notifications`. Прежние плоские имена и их алиасы удалены (`D-202`):
  соответствие — в [карте API](guide/api.md).
- **Несколько credentials и сессий.** `secrets.put_credential(kind, name=…)`,
  `secrets.credentials()`, `disable/enable/revoke_credential`, `verify/reject_credential`;
  сессии — `replace_session(..., mode="in_place"|"replace")`, `revoke_session`,
  `verify/reject_session`. Прежний единственный blob остался записью `default/default`.
- **Ревизия агрегата и `expected_revision`.** Команды изменения принимают `expected_revision`;
  несовпадение — `RevisionConflict`. Ревизия растёт на одну команду и попадает в события,
  вебхуки и read-схему.
- **Идемпотентность.** `idempotency_key` у аренды, операций и команд с секретами; секрет в ключ
  не попадает, только его HMAC-тег.
- **Фоновые работы.** `hub.workers.dispatch|maintenance|reconcile|provider_operations|acceptance`
  с `run_once(limit) -> WorkerRun`; `hub.dispatcher.run()`/`running()` и команды CLI — циклы
  поверх них. Библиотека не создаёт задач при импорте, создании хаба и `start()`.
- **Read-схема.** `hub.read` версионируется (`READ_SCHEMA_VERSION`) и содержит `identities`,
  `identity_links`, `leases`, `lease_history`, `region_states`, `events`, `proxies`,
  `proxy_bindings`, `credentials`, `sessions` — без секретов и служебных полей.
- **Ломающее в этой альфе:** `hub.workers.acceptance.run_once` возвращает `WorkerRun`, а не
  `int` (`D-327`); прежнее число — `run.processed`.

Полный список изменений по выпускам — в [CHANGELOG](../CHANGELOG.md).

## 4. Границы откатов

- Ревизии, которые только добавляют колонку, индекс или таблицу (`0008`, `0017`, `0018`, `0020`,
  `0028`, `0038`, `0039`), откатываются `downgrade` без потери пользовательских данных.
- `0022` (несколько credentials) откатывается только пока у аккаунтов нет записей, кроме
  `default/default`: иначе откат удалил бы секреты, которых в прежней схеме негде хранить.
- `0023` (история сессий) при откате оставляет по слоту одну, последнюю не отозванную запись;
  история теряется.
- `0033`–`0037` (режим хранения секретов) предполагают, что все секреты приведены к одному
  режиму: переключайте режим командой `identity-hub secrets convert`, а не откатом миграции.
- После любого `downgrade` запускайте `identity-hub doctor` до возвращения трафика.

## 5. Проверка после обновления

1. `hub.start()` проходит без `SchemaIncompatible` на всех процессах.
2. `identity-hub doctor` не показывает коллизий нормализации и расхождений ревизий.
3. `hub.read.version` совпадает с ожиданием приложения, которое читает read-схему.
4. Один проход каждой фоновой работы: `for worker in hub.workers: await worker.run_once(limit=1)`.
5. Производительность проверяется отдельно и только на изолированном стенде: бюджеты и
   критерий пригодности стенда — в [perf.md](perf.md) и решении `D-332`.
