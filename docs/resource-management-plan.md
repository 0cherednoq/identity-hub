## I1. `pool.eligible_count(among=…)` — ёмкость, включая занятые

### Что на самом деле в коде

Документ утверждает: «`capacity_detail()` считает только свободные, и тогда
собственная работа уменьшает долю». Первая часть верна, вторая — верный вывод, но
«получить ёмкость с занятыми невозможно» — преувеличение:

| Что | Где | Статус |
|---|---|---|
| `Pool.capacity()` / `Pool.capacity_detail()` → `PoolCapacity(free, reserved, available)` | `pool.py:351-363`, `:104-111` | только свободные |
| `StoreTx.count_candidates(query, limit)` — «сколько можно выдать сейчас» | `store/base.py:1405` | есть, free |
| `StoreTx.count_live_candidates(query, limit)` — «сколько подходящих имеют живую аренду» | `store/base.py:1408` | **уже есть**, используется только внутри `_unavailable_reason` (`lease.py:1373`) |
| `eligible` / `leased` / `free_eligible` в обзорах | `read/overview.py:67-69, 85-87` | **уже есть** в аналитике, но без `among=` и не на `Pool` |

То есть «пригодные, включая занятые» = `count_candidates + count_live_candidates`.
Оба примитива реализованы в обоих стораджах. Задача сводится к публичному методу.

### Почему это всё равно надо делать

Причина в документе правильная и это не косметика, а **ошибка контура управления**.
Если контур делит свободную ёмкость, то собственное потребление потребителя уменьшает
его же долю на следующем такте: занял 10 из 30 → видит ёмкость 20 → доля падает →
окно сокращается → работа останавливается → ёмкость растёт → окно растёт. Это
автоколебания. Делить нужно полную пригодную ёмкость, а конкуренцию за свободные
единицы разруливает аренда.

Та же логика в Kueue: доля считается от `nominal quota` и неиспользованной квоты
когорты, а не от мгновенно свободного.

### API

```python
# src/identity_hub/pool.py — Pool
async def eligible_count(
    self,
    *,
    for_operation: str | None = None,
    among: Select[Any] | Iterable[UUID] | Callable[[Identity], bool] | None = None,
    require_quota: bool = False,
    limit: int = 1_000_000,
) -> EligibleCapacity: ...
```

```python
@dataclass(frozen=True, slots=True)
class EligibleCapacity:
    eligible: int       # free + leased: вся пригодная ёмкость
    free: int           # можно выдать сейчас
    leased: int         # пригодные под живой арендой
    reserved: int       # keep_free: зарезервировано под приоритетную работу
    allocatable: int    # eligible - reserved: то, что контур вправе делить
```

Требования:

* `among=` принимает то же, что `Pool.lease(among=…)` (`pool.py:172,230`): список id,
  подзапрос read-схемы или предикат от `Identity`. **Иначе ёмкость и аренда разойдутся**:
  контур посчитает долю по одному множеству, а аренда будет брать из другого. Форму
  «предикат» разрешаем, но документируем, что она разворачивается в id через
  `_matching_ids` (`lease.py:1105-1118`) и на больших парках дорога — для контура
  использовать подзапрос;
* `for_operation=` и `require_quota=True` повторяют контракт `Pool.lease()`. Без
  `for_operation` значение `require_quota=True` отклоняется через `ValidationFailed`, потому
  что квотные окна определены правилом операции. Аккаунт с исчерпанной квотой не входит в
  делимую ёмкость;
* оба счёта читаются **в одной транзакции** (`StoreTx`), иначе `eligible` не
  согласован сам с собой;
* `limit` — страховка от полного скана на больших парках, как в `capacity_detail`.

### Пропущенное в документе: `reserve` / `keep_free`

У пула есть статический резерв свободных аккаунтов `Pool.reserve` / `keep_free`
(`pool.py:92-95, 130-131, 356-369`), и отказ `LeaseUnavailableReason.RESERVE`.
Если контур разделит `eligible` целиком, он выдаст окон на весь пул, задачи пойдут в
брокер, а аренда начнёт отказывать с `reason=reserve` — то есть работа будет
отправляться только чтобы вернуться через `defer`. Поэтому делимая величина —
`allocatable = eligible - reserved`, и именно её адаптер `capacity-governor`
подставляет в политику. Это поле обязательно в возвращаемом типе.

### Тесты

1. `eligible == free + leased` при любом числе живых аренд; `free` совпадает с
   `capacity()`;
2. занятие аренды не меняет `eligible` (меняет `free`/`leased`) — это ключевой тест
   против автоколебаний;
3. `among=` подзапросом и списком id дают одинаковый результат на одинаковом
   множестве;
4. `require_quota=True` исключает аккаунт с исчерпанной квотой;
5. `allocatable` уменьшается на `keep_free`;
6. забаненный / в карантине / COOLING аккаунт не попадает в `eligible`;
7. паритет `MemoryStore` и PostgreSQL (`src/identity_hub/testing/memory.py` против
   `postgres/store.py`).

## I2. Событие роста ёмкости

### Что в коде

Подтверждено: в каталоге событий группа «pool» содержит ровно два события —
`pool.capacity.low` (WARNING) и `pool.capacity.empty` (CRITICAL)
(`events/catalog.py:90-95`). `Pool._check_capacity` (`pool.py:371-401`) публикует
событие только когда `state != "ok"` (`pool.py:381-382`); при возврате в «ok»
внутреннее `_capacity_state` сбрасывается молча.

Поэтому контур узнаёт о падении ёмкости сразу, а о появлении аккаунтов — только на
следующем такте. Асимметрия: деградация событийна, восстановление — опрос.

### Что сделать

* добавить в каталог `pool.capacity.ok` (уровень INFO) — переход `low|empty → ok`;
* публиковать его в `_check_capacity` на обратном переходе, по тому же `_capacity_state`,
  который уже ведётся. Событие **только на переходе**, не на каждом замере — иначе
  каждый возврат аренды будет будить контур;
* в payload — `pool`, `service`, `space`, `previous_state`, `eligible`, `free`.
  Контуру нужен не факт, а новая ёмкость: тогда `kick()` не потребует дополнительного
  чтения;
* точки, которые должны приводить к проверке: создание аккаунта, выход из карантина /
  COOLING, снятие бана, возврат аренды, пополнение квотного окна. Если `_check_capacity`
  вызывается не на всех этих путях — дополнить (проверить при реализации).

### Приоритет — низкий

Контур с тактом 5 секунд работает и без события; событие сокращает задержку реакции
с секунд до мгновения. Делать **после** I1 и после того, как контур поедет (§15
документа ставит это пунктом 8 — согласен).

Гистерезис события — на стороне `capacity-governor` (G5): события ёмкости только
вызывают `kick()`, а решение «менять ли окна» принимает мёртвая зона политики.
Иначе одно пополнение вызовет серию пересчётов.

## I3. Пропущенное в документе: классификация отказов неполна

§5.2 документа сопоставляет реакции двум причинам отказа — `busy` и `no_candidates`.
В коде `LeaseUnavailableReason` (`enums.py:108-115`) **пять** значений, и каждое
требует своей реакции. Без этого задача получит отказ, который не обработан, и упадёт
в ретрай брокера — то есть ровно та потеря попыток, от которой избавляет `defer`.

| `reason` | Смысл | Реакция задачи |
|---|---|---|
| `BUSY` | пригодные есть, все заняты | `lease(wait=…)`, затем `item.defer(reason="busy")` — короткая задержка |
| `NO_CANDIDATES` | пригодных нет совсем | `item.defer(reason="no_resources")`, контур ставит окно 0 |
| `QUOTA` | квоты исчерпаны у всех пригодных | `item.defer(until=…)` по ближайшему окну квоты, не по фиксированной задержке |
| `NO_PROXY` | аккаунты есть, прокси нет | `item.defer(reason="no_proxy")` — **это дефицит другого ресурса**, у него своя ёмкость и своё пополнение |
| `RESERVE` | свободные есть, но они под `keep_free` | `item.defer(reason="reserve")`; если это происходит часто, контур делит ёмкость без вычета резерва — ошибка конфигурации (см. I1) |

Это не доработка библиотеки, а доработка **документа и рецепта в `docs/guide/`**:
таблица §5.2 resource-management.md должна быть расширена до пяти причин, а
`QuotaExhausted.retry_at` — отличён от `LeaseUnavailable(reason=QUOTA)`.

`NO_PROXY` заодно подтверждает правоту §3 документа: политика раздачи не может жить в
Identity Hub, потому что дефицитным бывает не аккаунт.

## I4. AIMD-лимит на провайдера — отложить, но границы уточнить

### Что в коде

Подтверждено отсутствие: адаптивного лимита нет. Есть статические механизмы —
`Throttle` (GCRA, `service.py:145-163`), `Quota` (`service.py:116-142`), фиксированное
окно `Availability.COOLING` по `retry_after` (`operation.py:74-80`).

### Важное ограничение, которого нет в документе

Identity Hub **не делает сетевых вызовов** — это прямо заявлено в README: «сетевой
вызов выполняет код приложения, а Identity Hub решает, какой аккаунт можно взять, и
фиксирует результат операции». Значит классический AIMD «+1 за успех, ×½ при 429»
здесь не может быть замкнут внутри библиотеки: нет точки, где измеряется исход.

Замыкать контур надо на уже существующем пути отчёта: `Operation` + `ErrorClassifier`
(`protocols.py:328-369`) + `apply_fault_effects` (`operation.py:271-323`). То есть
AIMD-лимит — это состояние на сервисе/пуле, которое:

* увеличивается на 1 при успешном `operation.__aexit__` без `Fault`;
* делится на 2 при `Fault` с `Blame`, означающим перегрузку провайдера
  (`retry_after` / 429 / flood-wait — уже распознаются и дают `COOLING`);
* нижняя граница 1, верхняя — настройка; применяется как динамический потолок
  параллельности на сервис, рядом с `Throttle`.

Сравнение с опорными реализациями (`talyho/docs/resource-management-research.md`): Netflix `concurrency-limits`
даёт AIMD и gradient-варианты, из портов живые — Regulator (Elixir), tower-acc (Rust).
Брать стоит простейший AIMD, а gradient/Vegas — нет: для него нужны замеры задержки
с низким шумом, которых у нас нет, потому что между нами и провайдером стоит
прикладной код.

### Решение

Отложить, как и предлагает документ. Условие возврата: появился провайдер без
документированных лимитов, по которому `COOLING` срабатывает чаще N раз в сутки.
До этого статического `Throttle` достаточно.

## I5. Резерв количества «оценка → факт» — отложить

### Что в коде

Подтверждено отсутствие. Единственный «резерв» — `Pool.reserve` / `keep_free`
(`pool.py:92-95`): статическое число свободных аккаунтов под приоритетную работу,
не оценка расхода. Квоты и `Throttle` списывают фиксированную стоимость.

### Когда понадобится

Только для провайдеров с переменной ценой запроса. В эталонных сценариях документа
(§1) такого нет: проверка домена стоит фиксированно, отправка письма — одна единица.
Балансовый случай решён иначе и правильно: §5.3 документа пишет **абсолютное значение
баланса под эксклюзивной арендой**, а не декремент, и гонок там нет по построению.

Отложить. При возврате — брать модель Sidekiq Enterprise points-лимитера (списать
оценку, по факту скорректировать), ссылка в `talyho/docs/resource-management-research.md`.

## I6. Устаревшая строка в §13 документа

Документ в «найденных проблемах» перечисляет: «типизация
`IdentityCreate(service=Service[...])` не принимает конкретный сервис из-за
инвариантности дженерика; пока `service=SERVICE.name`».

**В текущем коде этой проблемы нет.** `IdentityCreate.service` аннотирован
`str | Service` (`api/identities.py:155`) — непараметризованным `Service`, именно это
и снимает инвариантность; `service_name` обрабатывает оба варианта
(`api/identities.py:175-177`). Передавать конкретный объект сервиса можно, обходной
путь через `.name` не нужен.

Действие: строку из §13 убрать, в `CHANGELOG`/traceability Identity Hub при желании
отметить как исправленное. Прикладной код, который использует обход `SERVICE.name`,
можно упростить.

## Контракт реализации

Эти решения фиксируют границы работы до начала кода.

1. Новая очередь использует идентификаторы `RM*`. Код и checkpoint одной задачи попадают в один
   коммит с сообщением `feat(RM<номер>): <краткое описание>`; документационные задачи используют
   `docs(RM<номер>): ...`.
2. `EligibleCapacity` является новым публичным типом. Существующий `PoolCapacity(free,
   reserved, available)` и методы `capacity()`/`capacity_detail()` не меняются.
3. `eligible_count()` принимает `for_operation`, `among`, `require_quota` и `limit`. Остальные
   фильтры пула уже находятся в самом объекте `Pool`; добавлять второй вариант фильтров не нужно.
4. `free` и `leased` считаются двумя существующими методами `StoreTx` внутри одной транзакции.
   Интерфейс Store, схема PostgreSQL и миграции не меняются.
5. Предикат `among=callable` сначала разворачивается в список UUID тем же постраничным алгоритмом,
   что аренда. Два итоговых счётчика выполняются в одной транзакции, но пользовательский предикат
   по определению вычисляется до неё. Для больших парков рекомендуется SQL-подзапрос.
6. `reserved` использует действующую семантику `_effective_reserve`, включая `reserve_strict`.
   Для полной ёмкости значение ограничивается `eligible`, а `allocatable = eligible - reserved`.
7. `limit` ограничивает каждый внутренний счётчик. При достижении лимита результат является
   насыщенным счётчиком, а не гарантированным размером всего парка. Это нужно явно указать в API.
8. Событие `pool.capacity.ok` не меняет решение о размере окна. Оно только будит внешний контур;
   гистерезис остаётся в `capacity-governor`.

Цель: создать воспроизводимую точку отсчёта и не смешать новый API с существующим

- Добавить падающие контрактные тесты импорта `EligibleCapacity` из `identity_hub` и сигнатуры

- Зафиксировать текущее поведение `capacity()` и `capacity_detail()` регрессионными проверками.
- Проверить отсутствие необходимости в миграции и изменении `Store`.
- Записать в checkpoint команды и результаты baseline.

**DoD:** старый контракт подтверждён тестами, новый контракт падает по ожидаемой причине, в
progress-файле сохранены результаты baseline.

### RM1.1 Реализовать `EligibleCapacity` и базовый `eligible_count()`

Зависит от `RM0.1`.

- Добавить frozen/slots dataclass `EligibleCapacity` в `src/identity_hub/pool.py`.
- Экспортировать тип из `src/identity_hub/__init__.py` и включить в `__all__`.
- Реализовать внутренний helper, который в одной транзакции вызывает `count_candidates()` и
  `count_live_candidates()` и возвращает согласованный снимок.
- Сохранить инварианты `eligible == free + leased` и
  `allocatable == eligible - reserved`.
- Не менять `PoolCapacity` и существующие метрики доступной ёмкости.

**DoD:** базовый подсчёт работает на MemoryStore и PostgreSQL; взятие и возврат аренды меняют
`free`/`leased`, но не меняют `eligible`.

### RM1.2 Выравнять фильтры ёмкости и аренды

Зависит от `RM1.1`.

- Добавить `for_operation`, `among`, `require_quota` и `limit` в публичный метод.
- Вынести разворачивание callable-предиката из `lease.py::_matching_ids` в общий внутренний
  helper, чтобы аренда и подсчёт использовали один алгоритм.
- Проверить список UUID, PostgreSQL `Select` и callable на одинаковом наборе аккаунтов.
- Проверить квоты операции, lifecycle, standing, auth, required factors, бан, карантин,
  `COOLING`, proxy policy и фильтры самого пула.
- Проверить обычный и строгий `reserve`, включая `allocatable == 0`.

**DoD:** `eligible_count()` и `lease()` работают на одном множестве кандидатов; тесты обоих
Store проходят с одинаковыми ожидаемыми результатами.

### RM1.3 Описать API и интеграционный рецепт

Зависит от `RM1.2`.

- Показать рекомендуемый SQL-подзапрос `among=` и предупредить о стоимости callable.

**DoD:** интегратор может скопировать пример, посчитать окно по `allocatable` и арендовать из
того же `among` без расхождения выборок.

### RM2.1 Документировать все причины отказа аренды

Не зависит от `RM1.*` и может выполняться отдельно.

- Расширить таблицу в `docs/guide/07-leases.md` до `BUSY`, `NO_CANDIDATES`, `QUOTA`,
  `NO_PROXY`, `RESERVE`.
- Для каждой причины указать `defer`-стратегию и источник восстановления ресурса.
- Отдельно описать `LeaseUnavailable(reason=QUOTA, retry_after=...)` и
  `QuotaExhausted.retry_at`, чтобы потребитель не смешивал две формы ожидания.
- Подготовить краткий handoff для внешнего `talyho/docs/resource-management.md` без изменения
  чужого репозитория из этой очереди.

**DoD:** локальный guide покрывает все значения `LeaseUnavailableReason`; тест документации или
traceability не позволяет снова сократить таблицу до двух причин.

### RM2.2 Удалить устаревший обход типизации

Не зависит от `RM1.*`.

- Проверить примеры Identity Hub на `IdentityCreate(service=SERVICE.name)`.
- Где объект `Service` уже доступен, использовать `IdentityCreate(service=SERVICE, ...)`.
- Подготовить handoff для удаления устаревшей строки §13 в Tallyho.
- Не менять случаи, где строковое имя является фактическим входом конфигурации.

**DoD:** локальные примеры показывают поддерживаемый объект `Service`, а внешний документ получает
однозначную правку без необоснованной массовой замены строковых имён.

### RM3.1 Добавить переход `pool.capacity.ok`

Зависит от `RM1.2`. Выполняется после первого рабочего запуска governor.

- Добавить `pool.capacity.ok` уровня INFO в каталог событий.
- На переходе `low|empty -> ok` публиковать одно событие с `pool`, `service`, `space`,
  `previous_state`, `eligible`, `free`.
- Не публиковать событие при повторном измерении состояния `ok`.
- Переиспользовать внутренний подсчёт RM1, чтобы payload и публичный API не расходились.
- Покрыть переходы `ok -> low -> ok`, `ok -> empty -> ok` и отсутствие дублей.

**DoD:** событие возникает ровно один раз на восстановление и проходит catalog/outbox/dispatcher
контракты.

### RM3.2 Проверить точки пробуждения governor

Зависит от `RM3.1`.

- Добавить немедленную проверку после возврата аренды там, где объект `Pool` доступен.
- Проверить создание аккаунта, снятие бана, выход из карантина/`COOLING` и открытие квотного
  окна. Для путей без конкретного объекта `Pool` не вводить глобальный реестр пулов скрытно:
  записать ограничение и оставить периодический tick governor как страховку.
- Убедиться, что ошибки проверки ёмкости не ломают освобождение аренды и доменные команды.
- Добавить интеграционный тест `event -> kick`, если `capacity-governor` доступен в workspace;
  иначе сохранить точный handoff и ожидаемый payload.

**DoD:** все технически доступные точки дают раннее пробуждение, а недоступные явно перечислены;
периодический tick остаётся обязательным fallback.

### RM4.1 Финальная приёмка и передача интеграторам

Зависит от `RM1.3`, `RM2.1`, `RM2.2`, `RM3.2`.

- Прогнать targeted conformance на MemoryStore/PostgreSQL, typing и event pipeline.
- Запустить полный `bash scripts/check.sh` по правилам `CLAUDE.md`.
- Повторить ключевую симуляцию: при постоянной полной ёмкости и спросе аренды меняют
  `free/leased`, но окно по `allocatable` не колеблется.
- Обновить changelog, traceability и handoff-документы Tallyho/capacity-governor.
- Закрыть очередь только после зелёного полного gate.

**DoD:** полный gate зелёный, симуляция не показывает автоколебаний, все задачи `RM*` имеют
терминальный статус.

## Сохранение прогресса

Единственный источник статуса очереди находится в
[`resource-management-progress.md`](resource-management-progress.md). При каждой сессии:

1. Прочитать checkpoint, таблицу задач, последние строки журнала, затем нужный раздел этого плана.
2. Если есть `in_progress`, продолжить с первого незакрытого шага. Иначе взять первую `todo`, у
   которой зависимости имеют статус `done`.
3. В начале задачи записать 3-8 проверяемых шагов и статус `in_progress`.
4. После каждого законченного шага поставить `[x]` и сохранить полезную заметку для следующей
   сессии. Не ждать завершения всей задачи.
5. Закрывать задачу и очищать checkpoint в том же коммите, где находятся код и тесты.
6. Статус `blocked` использовать только для внешней причины. Причину и безопасный следующий шаг
   записать в колонке «Примечание» и checkpoint.

Допустимые статусы: `todo`, `in_progress`, `done`, `blocked`, `cancelled`. Одновременно активна
не более чем одна задача. Отложенные AIMD и резерв количества не добавляются в активную таблицу,
пока не выполнено условие возврата.
